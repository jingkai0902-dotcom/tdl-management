## 一、材料一：从"AI 落地五环节"可借鉴什么

### 1.1 五个环节中，TDL 已经做到的

| 环节 | 材料原意 | TDL 当前状态 |
|------|---------|------------|
| 管理层主导 | AI 落地必须老板和管理者牵头 | ✅ 少巍和李珍主导，从需求到设计到试点推动 |
| 专家经验 AI 化 | 把专家能力蒸馏成工具，复制给团队 | ⚡ 正在做——08 号文档发现的核心差距就是"判断标准显性化"，16 号文档的 What+Who+When 三要素就是第一步 |
| 梳理业务流程 | 最容易忽略但最关键的环节 | ⚡ 正在做——从"抽任务"转向"先理解业务→严格分类→三要素判定"，每步都在深挖流程 |

### 1.2 值得 TDL 直接吸收的

**A. "业务资产统一出入口"**

材料原话：打破部门壁垒，建立数据、经验、知识等业务资产的跨部门流转机制，这是 AI 协同的基础架构。

TDL 当前只接收"会议纪要"这一种输入。材料给了一个明确的扩展方向：TDL 应该逐步成为管理层所有关键信息的统一入口——不只是会议，还包括述职报告、经营报表、绩效考核结果、招聘进度、销售数据摘要等。15 号文档的四层知识架构已经意识到了这个方向，但当前停在了设计层。

给 Codex 的评估点：在阶段 2（非任务对象流转）和阶段 3（知识层最小版本）之间，是否需要增加一个"多源输入适配层"的设计？还是一个输入源稳了再扩？

**B. "人做 AI 事则亏，AI 做人的事则险"**

这是一条可以写入 TDL 设计原则的简洁准则。

具体映射到 TDL：
- AI 做：会议内容分类、三要素判定、候选 TDL 生成、逾期检测、数据统计
- 人做：伪决议复核、辅导判断、战略决策、内容质量审核（最后防线）

当前 20 号文档 §2.3 的人机交接流程已经写了这些，但缺少一句顶层原则。建议加入 18 V2 或设计原则文档。

**C. 管理者无需密集跟进技术细节**

材料指出管理者的核心职责是判断技术方案的高效性、合理性、适配性，而不是学怎么做模型调参或 prompt 工程。

TDL 项目里已经验证了这一点：少巍不需要理解 ai_client.py 的实现细节，但他需要能判断"模型分层调用策略是否合理"和"会议分类的伪决议率是否符合预期"。当前的三方协作模式（Codex 报成本、Claude 报风险、少巍拍板）正是这种分工的落地。

### 1.3 少巍补充的方向

> "把专门的岗位 skill 化、把专门的业务流程化，这种淬炼本身就是一份财富。"

这个判断很关键。具体来说：

- **岗位 skill 化**：把赵晓华的教务执行力看板回收方法、时颖的销售产能排名逻辑、张皓的新师面谈归因框架——这些岗位具体动作中的判断方法和操作标准，提炼成可复用的 Skill。新的教务经理上任时，不只是继承一个"看板回收"的任务模板，而是继承一套完整的"怎么看、怎么评、怎么反馈"的 AI 工作流。
- **业务流程化**：把月度复盘会的完整流程（会前准备→会中记录→五类内容分类→会后追踪→下次复议）、薪资月度流程的 9 步（提交→审核→汇总→核验→拆分行→导出→确认→发放→归档）固化下来。

这两类资产列入 TDL 插件生态的候选：岗位 skill 包 = 插件层的"培训与管理赋能"方向；流程固化 = 插件层"企业节奏把控"的底层数据。

## 二、材料二：从 Michael 的 agent 养成可借鉴什么

### 2.1 首先说清楚什么不能直接借鉴

Michael 做的是**个人效率 agent**。他养 agent 的快节奏迭代（今天不好用今天就改）在 TDL 场景里不可行，因为：

- TDL 的每次变更影响 15 个人的使用体验，需要 PR 审核 + 部署验证
- TDL 的一条错误提醒会伤害管理者对系统的基本信任
- TDL 处理的是组织管理信息（绩效、辅导、风险），不能像个人调研工具那样随意试错

所以材料二里"打开 Claude Code 直接改 prompt 立刻生效"的做法，TDL 不能照搬。但下面的部分可以。

### 2.2 值得 TDL 借鉴的

**A. "任何沟通都要有上下文"——映射到 TDL 的会议录入**

Michael 的团队所有沟通都录音转文字，给 agent 提供完整上下文。这不是新技术——TDL 的月会纪要录入本质上做的就是这个。但材料提醒了一个点：上下文不只是"会议原文"，还包括说话人的身份、职责和当下的业务背景。

当前 TDL 的 meeting→decision→tdl 三层只存了内容，没有存"这句话是谁说的、ta 的岗位是什么、当时在管什么事"。这对会议分类和伪决议判断是有影响的——同样一句"我们得把续费率提上来"，从时颖口中说出和从李珍口中说出，含义完全不同。

给 Codex 的评估点：在会议内容 schema 中是否需要增加 speaker 字段和 speaker 的职务上下文？

**B. "把标准化工作流做成 skill"——TDL 已经在往这个方向走**

Michael 把"PDF/Word/PPT 转统一格式"写成一个 skill，不用每次手动处理。TDL 的 20 号文档已经规划了第一批 Skill（tdl-judgment-rules、meeting-classification-strict 等），做的就是同一件事——把重复发生、规则明确的工作固化。

但 Michael 的做法有一个 TDL 可以学的细节：他的 skill 特别窄。不是一个"文档处理大平台"，而是"上传→调 API→转换→改名→下载"这一个精确的流程链。当前 TDL 的 Skill 设计（如 meeting-classification-strict）范围是否太宽？是否应该拆成更小的原子 Skill（如"三要素判定""伪决议检测""证据片段提取"各为一个）？

给 Codex 的评估点：第一批 Skill 的粒度是否需要更细。

**C. "只配真正需要的 skill，不过度追求数量"**

Michael 说社区 skill 商店里几百个，他用到的就几个，其他全是他自己建的。这一点对 TDL 有直接价值：TDL 不应该追求 skill 数量，而应该追求每个 skill 都经过真实管理场景验证。

当前 20 号文档的第一批 Skill 清单（5 个）是克制的，这个方向对。后续每增加一个 Skill 都需要回答三个问题：它解决了什么真实问题？有没有样例验证？不做会有什么损失？

**D. "把老板布置任务的方式从'你先调研'改成'你布置给 agent'"**

这是材料二里最值得反思的一点。Michael 的老板对他说：你不要自己去调研，你把任务布置给 agent 去完成。

映射到 TDL 的当前开发模式：少巍把设计方向交给 Codex，Codex 展开实现方案，Claude 做可行性质疑，少巍拍板。这个模式已经接近"把任务布置给 agent"——但不是完全一样，因为少巍仍然需要自己消化外部材料（就像现在）、自己判断方向、自己把需求转成 Codex 能理解的格式。

一个可能的微调：后续少巍发给 Codex 的外部材料或需求方向，先让 Claude 做一次"对 TDL 项目的适用性评估"（类似本文档做的事），再让 Codex 基于评估结果展开。这样少巍不需要自己先消化完再转述，可以减少一道手工环节。

## 三、两个材料共同的线索

两份材料指向同一个核心逻辑：

1. **先有上下文**——材料一的"业务资产统一出入口"，材料二的"一切沟通都要录音"
2. **再做标准化**——材料一的"专家经验 AI 化 + 业务流程 AI 化"，材料二的"把 SOP 做成 skill"
3. **最后才自动化**——材料一的"AI 擅长大量数据处理和批量生成"，材料二的 agent 替人完成调研和文档处理

这个逻辑链在 TDL 里正是我们要走的：17 号（终局方向）→ 18 号（落地路线）→ 20 号（逐块展开）—先建上下文（五类会议分类）→ 再做标准化（Skill）→ 最后自动化（插件）。

## 五、Codex 评估结论

### 5.1 多源输入：纳入路线，但不提前开发

多源输入适配层是正确方向，但不应该插到会议录入跑稳之前。当前顺序应是：

1. 先把会议材料的五类分类、证据追溯、三要素判定跑准。
2. 再把述职报告、经营报表、绩效考核、招聘进度、销售摘要等材料作为“新输入源”逐个接入。
3. 每接入一种输入源，都必须先定义来源字段、可信边界、人工复核点和输出对象。

因此，多源输入应写入 20 号文档的阶段 2 到阶段 3 之间，定位为“多源输入适配层”，而不是当前开发项。

### 5.2 Skill 粒度：保留总 Skill 名，但拆成原子动作

`meeting-classification-strict` 作为总入口可以保留，但内部应拆成更窄的原子 Skill / 子流程：

1. `meeting-evidence-extraction`：只提取证据片段，不做业务判断。
2. `meeting-5w2h-gate`：只判断 What / Who / When 是否齐全。
3. `meeting-false-decision-review`：只审伪决议、愿望包装和深加工。

这样既保留用户能理解的总能力，又避免一个 Skill 变成大而全的会议分析平台。

### 5.3 Speaker 上下文：必须进入会议 schema

会议内容判定需要 speaker 和职务上下文。原因是同一句话由不同人说出，管理含义不同。

最低字段建议：

| 字段 | 作用 |
|---|---|
| `speaker_name` | 谁说的 |
| `speaker_role` | 当时岗位或职责 |
| `speaker_scope` | 负责的校区、部门或业务线 |
| `evidence_span` | 原文证据片段 |

这不会显著增加当前复杂度，因为 5 月材料已经包含人员提报和会议转录；先在 gold set 中人工标注即可，不急着建正式人员档案表。

### 5.4 岗位 Skill 化：列入插件生态，但放到后段

岗位 Skill 化非常有价值，但它依赖两个前置条件：

1. 已经能稳定识别“事实、已明确事项、议题、火花、观察线索”。
2. 已经积累了一批真实岗位动作和结果回收样例。

因此它不应作为当前开发主线，而应归入“管理者赋能与组织能力发展”插件下的能力包，阶段上放在管理者/员工档案字段稳定之后。

### 5.5 设计原则：建议写入 20 号和 18 V2

“人做 AI 事则亏，AI 做人的事则险”适合成为设计原则，但需要改写成更工程化的版本：

> AI 负责高频整理、分类、追踪和候选生成；人负责边界判断、价值判断、辅导判断和最终执行授权。

这条原则应写入 20 号文档的人机交接章节，并在 18 V2 中保留。

### 5.6 外部材料流程：建议保留 Claude 适用性评估

后续外部材料进入项目时，建议采用：

```text
外部材料 → Claude 适用性评估 → Codex 吸收与落地拆解 → Frank 拍板 → PR
```

这样可以减少 Codex 直接把外部材料工程化的风险，也符合当前三方分工：Claude 做风险和可行性质疑，Codex 做落地展开，Frank 做业务判断。
