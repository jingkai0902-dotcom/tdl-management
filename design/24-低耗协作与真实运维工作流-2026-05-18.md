# 24 · 低耗协作与真实运维工作流 — 2026-05-18

## 一、本文结论

本项目后续默认采用以下顺序推进：

1. 能用脚本解决的，不重复手拼命令。
2. 能用命令行、API、数据库和仓库文档确认的，不先打开第三方 UI。
3. 只有真实界面、真实登录态或最后一公里体验验证必须依赖 UI 时，才考虑 `Computer Use`。
4. `Computer Use` 不再作为默认动作；需要使用时，Codex 先说明原因、收益和替代方案，再由 Frank 决定是否使用。
5. 简单机械任务优先考虑便宜模型；复杂设计、跨模块判断、生产风险和高影响决策继续使用强模型。

目标不是单纯“少用额度”，而是把额度集中用在真正需要判断力的地方。

## 二、默认工具优先级

| 优先级 | 工具类型 | 适用场景 |
|---|---|---|
| 1 | 已有脚本 | 部署、smoke test、生产检查、重复性巡检 |
| 2 | 命令行 / API / 数据库 | GitHub 状态、服务状态、配置读取、日志、数据库事实 |
| 3 | 仓库文档 / Skill 引用 | 固定流程、既有结论、长期规则 |
| 4 | 浏览器页面读取 | 需要登录态但仍可结构化检查的后台页面 |
| 5 | `Computer Use` | 真实桌面端、无法结构化读取的 UI、最终体验验收 |

执行原则：

1. 默认先走 `1 -> 2 -> 3`。
2. 一旦某个动作连续重复两次，就评估是否值得脚本化。
3. 一旦某个 UI 路径被摸清，就沉淀到文档或 Skill，不再让后续对话重新探索。

## 三、哪些事情应该脚本化

当前已经固定的高频动作：

| 动作 | 默认入口 |
|---|---|
| 生产健康检查 | `scripts/tdl-prod-check.sh` |
| 生产部署 + smoke test | `scripts/tdl-deploy-prod.sh` |
| 代码测试 | `PYTHONPATH=. .venv/bin/pytest -q` |
| PR 状态查看 | `gh pr view ...` |

后续如果继续重复出现，也应优先脚本化：

1. 指定 TDL 的状态 + 审计日志查询。
2. 真实钉钉验证前的测试数据准备。
3. 试点指标提取。
4. 会议 gold set 评测。

## 四、哪些事情适合做成 Skill

Skill 只承载“高复用流程”，不承载整套项目背景。

当前适合沉淀为 Skill 的内容：

1. `tdl-live-ops`
   - 何时读取哪些文档。
   - 默认先跑哪些脚本。
   - 真实钉钉验证前的最小检查顺序。
2. 后续如果 PR 流程继续频繁复用，再补 `pr-review-coordination`。

不适合做成 Skill 的内容：

1. 一次性排障结论。
2. 很长的历史背景。
3. 仍在快速变化的产品判断。

## 五、`Computer Use` 的新规则

此前项目里，为了省事，Codex 会直接用 `Computer Use`：

1. 向 Claude 桌面端发送 PR review 请求。
2. 在飞书 / 钉钉后台修改权限或配置。

从 2026-05-18 起，默认规则调整为：

1. **先判断能否不用 UI。**
   - 能用 CLI、API、数据库、文档或脚本完成，就不使用 `Computer Use`。
2. **如果确实需要 UI，先提示 Frank。**
   - 说明“为什么现在需要 UI”“准备做什么”“如果不用 UI 会缺什么证据”。
3. **由 Frank 决定是否启用。**
   - 没有明确确认时，Codex 不把 `Computer Use` 当默认路径。
4. **若使用 UI，只做必要动作。**
   - 不在 UI 中做长时间探索。
   - 先用命令行和文档把范围缩到最小，再进入界面。

典型需要先提示 Frank 的场景：

| 场景 | 为什么需要提示 |
|---|---|
| 把 PR 发给 Claude 桌面端 | 可改由 Frank 手动转发，或等更低成本方式 |
| 改飞书 / 钉钉后台权限 | 属于第三方管理后台操作 |
| 真实客户端按钮验收 | UI 证据必要，但应说明为何必须做 |

## 六、模型选择建议

后续每一轮如果任务明显属于以下几类，Codex 先给出一句模型建议，再继续执行：

| 任务类型 | 默认建议 |
|---|---|
| 小改文案、查日志、跑脚本、整理结果 | 优先便宜模型 |
| 单文件小修、小范围测试补强 | 可用中档模型 |
| 架构判断、跨模块改动、生产事故、复杂产品取舍 | 使用强模型 |
| 涉及用户体验和真实业务边界的高影响决策 | 使用强模型 |

提示模板：

```text
这一步是低复杂度机械任务，建议用便宜模型即可；如果你更在意速度或想保守一点，也可以继续用当前模型。
```

或：

```text
这一步涉及跨模块判断和真实生产风险，建议继续用强模型，不值得为了省额度降档。
```

## 七、Agent 的使用边界

Agent 主要解决并行，不默认解决省额度。

适合使用 Agent：

1. 两个任务彼此独立。
2. 写入范围完全分离。
3. 并行后能明显缩短关键路径。

不适合使用 Agent：

1. 小任务。
2. 多个 Agent 都要重复读取同一批背景。
3. 关键路径下一步就依赖某个结果。

## 八、当前项目的直接落地

本次调整后，后续默认顺序为：

```text
先读当前最相关文档
→ 先跑已有脚本或命令行
→ 判断是否需要 Skill
→ 如确需 UI，再向 Frank 说明并征求是否使用
→ 最后才进入真实端验证
```

当前已落地的配套项：

1. `scripts/tdl-prod-check.sh`
2. `scripts/tdl-deploy-prod.sh`
3. 本文档
4. 本地 Skill：`tdl-live-ops`（位于 Codex 本地技能目录，不在本仓库内）

## 九、判断标准

这套调整是否有效，不看形式，看四个结果：

1. 同类任务下次是否明显少读背景。
2. 同类操作是否明显少拼命令。
3. `Computer Use` 是否只出现在确实需要真实 UI 的节点。
4. 额度是否更多花在产品判断、代码质量和真实验收，而不是重复摸索。
