# 26 · 架构蓝图建议评估与分阶段采纳 — 2026-05-21

## 一、本文定位

本文记录 Frank 使用 AntiGravity 最新模型对 TDL 项目做出的架构与经营蓝图建议，以及 Claude、Codex 对该建议的交叉评估结论。

本文不是新的开发任务清单，也不替代 `18-项目落地实现路径-V2-2026-05-18.md` 和 `19-系统板块重梳与PR推进计划-2026-05-18.md`。它的作用是：

1. 保留外部架构建议中有价值的中长期素材。
2. 明确哪些建议近期吸收，哪些只作为阶段 3 / 阶段 4 参考。
3. 防止后续 PR 误把远期蓝图当成当前开发范围。
4. 为 PR-E 之后的功能恢复提供优先级依据。

当前硬边界仍然不变：

1. 不新增知识层正式数据库表。
2. 不开发战略对齐、经营复盘、管理者画像等上层插件。
3. 不引入 Redis / Celery 等新基础设施，除非单机方案被真实数据证明不够。
4. 不把 OKR / KR 强绑定提前写进 TDL 主表。
5. 不把会议材料中的意向、倡导、方向感包装成已决议。

## 二、三方评估共识

AntiGravity 的六类建议中，Claude 与 Codex 的判断高度一致：

| 建议 | 采纳级别 | 当前结论 |
|---|---|---|
| HITL 纠错差值沉淀 | 近期吸收 | 高价值，直接服务试点质量和评测集生长 |
| 异步解耦 | 近期技术候选 | Stream handler 同步等待 LLM 是 pilot 风险，应优先做轻量单机队列 |
| 管理陷阱防御 | 近期写入原则 | 先写入架构底线，代码实现等数据积累后再做 |
| 知识图谱 / nodes-edges | 阶段 3 草案 | 方向正确，但现在不能建正式表 |
| TokenJuice 会议管道 | 阶段 3 预研 | 适合会议录入，不适合日常 TDL；必须保留原文证据 |
| OKR / KR / CPM / TOC 插件 | 阶段 4 参考 | 理论可用，但当前没有真实维护的 OKR 数据源 |

## 三、近期采纳项

### 1. 异步解耦：提升为 PR-E 后的高优先级候选

当前钉钉 Stream bot 主入口在 `TDLChatbotHandler.process()` 中调用 `intake_dingtalk_message()`，而 intake 流程会等待 LLM 提取结果。真实试点中，这会带来三个风险：

1. 用户感觉机器人响应慢。
2. Stream 连接超时或重试时，可能触发重复处理。
3. LLM 抖动会直接影响钉钉入口稳定性。

采纳方向：

```text
收到消息 -> 写入 Postgres 队列表 -> 快速 ack -> 单机后台 worker 消费 -> 发送卡片
```

第一版约束：

1. 使用 PostgreSQL 行锁队列，例如 `SELECT FOR UPDATE SKIP LOCKED`。
2. 不引入 Redis、Celery、Kafka。
3. 先覆盖普通消息 intake，不动按钮 callback。
4. 必须设计幂等键，避免钉钉重试导致重复创建。
5. 必须记录 received / processing / done / failed 状态和错误原因。
6. 上线前先检查生产日志，确认慢响应或重试是否真实发生、频率多高。

这不是远期架构幻想，而是当前 pilot 可遇到的入口稳定性问题。但实现仍应小步做，不一次性改成复杂任务平台。

### 2. HITL 纠错差值沉淀：作为数据飞轮入口

Frank 和李珍对草稿的修改，是比模型自评更有价值的训练样本。当前系统已经开始处理：

1. follow-up 纠错。
2. owner / due_at / completion_criteria 覆写。
3. 英文名与语音别名。

下一步应该把“AI 初稿 -> 用户修正 -> 最终 TDL”的差值沉淀下来。

第一版建议字段：

| 字段 | 说明 |
|---|---|
| `raw_text` | 用户原始输入 |
| `draft_payload` | AI 第一版草稿 |
| `confirmed_payload` | 最终确认或更新后的结果 |
| `diff_fields` | 字段级差异，如 owner_id / due_at / completion_criteria |
| `action_type` | direct_confirm / modified_confirm / canceled / follow_up_update |
| `source` | dingtalk_msg / card_callback / follow_up |
| `created_by` | 操作者 |
| `created_at` | 记录时间 |

第一阶段只要求记录，不要求自动生成 Gold Set。等累计到足够样本后，再离线筛选困难样本，进入回归评测集。

### 3. 管理陷阱防御：写入长期底线

当系统从“帮我记事”扩展到“管理追踪与画像”时，组织会自然出现规避行为：

1. 任务注水：创建大量低价值任务冲高完成率。
2. deadline 操纵：故意拉长截止日期或频繁暂缓。
3. 任务线下化：真正困难的工作不录入系统。
4. 卡片冷处理：不确认、不反馈，让系统失去输入。

当前不实现评分、惩罚或自动管控，但必须确立底线：

> 工具属性永远优先于管理追踪属性。系统首先要让管理者愿意继续使用，而不是为了画像统计压迫用户。

未来进入管理者画像或经营插件前，必须先设计防博弈机制。尤其是“系统坏死防线”：如果用户连续多次不处理 AI 草稿或提醒，系统应降低主动追问和追踪强度，退回更被动的记事本模式，直到用户显式恢复。

## 四、中期预研项

### 1. 会议材料分段提取管道

AntiGravity 提出的 TokenJuice / MapReduce 管道方向正确，但三阶段、多次 LLM 调用对当前阶段偏重。

更适合本项目的中期路线：

```text
原文保留 -> 规则预处理 -> 分段候选提取 -> 证据锚点输出 -> schema 校验 -> 人工复核
```

关键要求：

1. 降噪只用于候选提取，不能替代原文证据。
2. 每个候选必须带 `evidence_span`。
3. 没有原文证据的候选直接废弃。
4. 会议内容仍按 `事实 / 已明确事项 / 待处理议题 / 火花设想 / 观察线索` 分类。
5. 不满足 `What + Who + When` 的内容不能进入 TDL 草稿。

### 2. Postgres 轻量图模型

`k_nodes / k_edges` 作为未来知识层草案有价值，但当前不能实现为正式迁移。

保留判断：

1. 轻量属性图适合阶段 3 的知识层最小版本。
2. Postgres JSONB + 递归 CTE 可以先支撑小规模关系查询。
3. “毫秒级响应”不能作为长期承诺，必须看数据量、索引、递归深度和边类型。
4. 后续是否引入独立图数据库，必须等 Postgres 方案遇到明确瓶颈再判断。

## 五、远期参考项

### 1. OKR / KR 强绑定

Objective / Key Result 的分层对战略管理有价值，但当前不具备前提：

1. 组织没有在系统内维护稳定 OKR 数据源。
2. 日常 TDL 主链路仍在 Frank + 李珍试点。
3. 会议录入仍在 schema / gold set 阶段。
4. 现在给 TDL 加 `aligned_kr_id` 会提前制造战略管理负担。

因此，OKR / KR 只作为阶段 4 插件素材，不进入近期 schema。

### 2. 经营插件模型

关键路径法、约束理论、组织阻力归因矩阵等模型可以作为未来插件的分析方法，但前提是：

1. TDL 状态、结果回收、暂缓原因、阻塞原因足够稳定。
2. 任务依赖、目标、事实源能够追溯。
3. 管理者画像有明确授权和使用边界。

没有这些前提，插件会退化成“看起来专业但无法服众的 AI 建议”。

## 六、对 PR-E 优先级的影响

PR-E 恢复功能开发时，候选优先级调整为：

1. Postgres 单机 intake queue：降低 Stream 入口等待 LLM 的稳定性风险。
2. HITL intake diff：沉淀用户纠错和最终确认差异。
3. follow-up 纠错与人名匹配继续打磨：围绕真实试用错例迭代。
4. 会议分类 schema / evaluator：继续推进证据锚点与伪决议拦截。
5. 按钮体验修复：原卡灰态、原位刷新、反馈入口。

其中 1 和 2 都应先写窄，不引入新基础设施，不扩大到知识层正式建表。

## 七、明确不采纳为当前任务

以下内容本轮不进入开发：

1. `k_nodes / k_edges` 正式表。
2. Neo4j 或其他独立图数据库。
3. Redis / Celery / Kafka 队列。
4. OKR / KR 表和 `aligned_kr_id` 字段。
5. 管理者评分、排名或自动绩效判断。
6. 自动经营策略建议插件。
7. 对会议材料自动批量创建正式 TDL。

## 八、后续协作方式

外部材料继续按以下方式进入项目：

```text
外部材料 -> Claude 适用性评估 -> Codex 吸收与落地拆解 -> Frank 拍板 -> PR
```

这能保留三方分工：

1. Claude 负责风险、边界和可行性质疑。
2. Codex 负责工程落地拆解、测试方案和 PR。
3. Frank 负责业务判断、阶段优先级和最终拍板。

本文合并后，后续新对话看到 AntiGravity 的架构建议时，应以本文为采纳口径，不应重新从头解释或直接实现远期蓝图。
