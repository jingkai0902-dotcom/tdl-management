# 11 · 模块化架构方案

> 与 03 的关系：本文在 03-功能模块 的五模块基础上，定义模块间接口契约和插件化扩展体系。
> 与 06 的关系：本文不改变 06-开发计划 的批次顺序，但补充每个批次的验收标准和模块边界定义。
> 与 10 的关系：Codex 和 Claude 的协作 SOP 不变，本文补充「Codex 交付什么才算一个模块完工」的标准。

---

## 一、概述

### 为什么要做模块化改造

当前系统在代码组织上已经做到了 model / service / router / integration 四层分离，结构是干净的。但存在三个实际问题：

1. **少巍无法独立验证单个模块**：必须等整个链路跑通才能判断"AI 做到了什么程度"。比如意图捕获模块的字段提取准确率，目前只能在钉钉里一条条测，没有离线批量验收手段。
2. **模块边界在代码里是模糊的**：`intake_service.py` 直接 import `tdl_service.create_draft_tdl` 和 `calendar_service.create_tdl_with_calendar`——从调用链上看不出模块边界。后续改一个模块容易牵动其他模块。
3. **扩展能力受限**：第 2 阶段的五项需求（老板督导航面板、管理者能力成长档案、TDL 模板结构校准 AI、周期性项目、会前准备能力）加上少巍新提出的管理战略分析、统筹任务优化、任务结果回收——如果继续往现有 service 里堆，代码会快速膨胀，改动风险越来越高。

### 本文档做什么

定义三层改造方案，逐层推进，不推倒重来。三层加起来核心代码改动量不超过 200 行，重点在架构纪律和验收标准，不在大规模重构。

## 二、现状诊断

### 当前做得好的

```
app/
├── models/     ← 数据模型独立，字段完整，与 02 号文档对齐
├── services/   ← 业务逻辑按 GTD 五步做了初步拆分
```

数据模型层面，meeting → decision → tdl 三层分离已经做到，状态机完整，审计日志从第一天就有。这些是后续模块化的良好基础。

### 当前耦合点

| 耦合位置 | 具体表现 | 风险等级 | 是否需要解 |
|----------|---------|---------|-----------|
| 数据模型共享 | 所有 service 操作同一套 SQLAlchemy 模型 | 低 | 不需要——这是必要的共享内核 |

| 配置散读 | 多个 service 各自调 `load_yaml_config` | 低 | 可优化——集中注入 |

```
   │           │       │           │      │           │
   └───────────┘       └───────────┘      └───────────┘
        │                                       │
        │ 写入草稿                               │ 读取状态
        ▼                                       ▼
   ┌─────────────────────────────────────────────────┐
   │                  TDL 数据存储                      │
   │              (tdl_service.py)                    │

                          │
        ┌─────────────────┼─────────────────┐
        │                 │                 │
   ┌────▼─────┐     ┌────▼─────┐     ┌────▼─────┐
   │ 4.复盘可见 │     │ 5.沉淀进化 │     │ 日历写入   │
   │  review   │     │  evolve   │     │ calendar  │
   └───────────┘     └───────────┘     └───────────┘
```

关键设计决策：
- **模块 1-2-3 是主链路**：意图捕获 → 结构化处理 → 进度推进，数据流经 TDL 存储
- **模块 4 只读不写**：周报统计从存储读数据，不产生新 TDL
- **模块 5 是数据消费者**：从模块 1-4 积累的数据中提取洞察，MVP 不开发功能但数据库已预留字段
- **日历写入是横切关注点**：挂在 TDL 创建事件上，不构成独立模块

### 4.2 各模块独立验收标准

#### 模块一：意图捕获

| 验收项 | 标准 | 验收方式 |
|--------|------|---------|
| 字段提取准确率 | title ≥ 90%, owner ≥ 80%, due_at ≥ 75% | 离线跑 50 条预标注测试语料 |
| 自动创建/草稿分流 | 高置信度自动创建、低置信度转草稿的分流正确率 ≥ 95% | 同批语料验证分流逻辑 |
| 会议纪要批量拆解 | 单次月会纪要产出 ≥ 5 条 TDL 草稿，每条含负责人 | 用往期真实会议纪要测试 |
| 异常兜底 | AI 返回空 → 退化为草稿卡片（不崩溃）；非文本消息 → 提示"当前支持文字录入" | 手工触发异常场景 |

#### 模块二：结构化处理

| 验收项 | 标准 | 验收方式 |
|--------|------|---------|
| 标签分类准确率 | 对照标签词典，分类准确率 ≥ 85%，< 70% 标"待确认" | 50 条预分类语料 |
| 不编造的硬约束 | 输出标签值 100% 在词典内，不出现词典外的业务线/职能域/产品线 | 自动校验输出合法性 |
| 缺失检测 | owner 缺失 → 追问, due_at 缺失 → 追问, completion_criteria 缺失 → 建议但不追问 | 规则校验 |

#### 模块三：进度推进

| 验收项 | 标准 | 验收方式 |
|--------|------|---------|
| 每日提醒触发时间 | 按班制路由，各时点误差 < 5 分钟 | 单元测试覆盖所有班制+周二特殊情况 |
| 逾期升级链路 | 逾期 1 天提醒 → 2 天追问 → 3 天标记"待关注" | 时间模拟测试 |
| 卡片按钮状态流转 | 已完成/延期/需协助/暂缓 四种操作→状态正确变更 | 集成测试 |
| 暂缓恢复 | snooze_until 到期后状态恢复为 active | 时间模拟测试 |

#### 模块四：复盘可见

| 验收项 | 标准 | 验收方式 |
|--------|------|---------|
| 数据准确性 | 本周新增/完成/逾期/延期/等待/阻塞 各数字与数据库一致 | 准备已知数据集跑周报 |
| 超 3 天未推进识别 | 正确列出所有未推进超过 3 天的 TDL | 同上 |
| 推送时机 | 每周一 09:00（北京时间）± 5 分钟 | 调度器单元测试 |

## 五、第二层：接口契约层

### 5.1 核心思路

不拆服务、不引入消息队列、不搞微服务。在当前单体里做一件事：**每个模块只依赖接口，不依赖实现**。

用 Python `Protocol` 定义每个模块对外暴露的契约。模块间调用从直接 import 实现类改为依赖注入接口。

### 5.2 接口定义（精简版）

```python
# contracts/tdl_store.py —— TDL 存储接口

from typing import Protocol, runtime_checkable

@runtime_checkable
class TDLStore(Protocol):
    """模块 1/2/3 通过这个接口读写 TDL，不直接调 tdl_service"""

    async def create_draft(self, payload: TDLDraftCreate) -> TDL: ...
    async def confirm(self, tdl_id: UUID, actor_id: str) -> TDL: ...
    async def complete(self, tdl_id: UUID, actor_id: str) -> TDL: ...
    async def postpone(self, tdl_id: UUID, due_at: datetime, actor_id: str) -> TDL: ...
    async def snooze(self, tdl_id: UUID, until: datetime, actor_id: str) -> TDL: ...
    async def list_open(self, owner_id: str) -> list[TDL]: ...
    async def get(self, tdl_id: UUID) -> TDL | None: ...
```

```python
# contracts/message_port.py —— 消息推送接口

@runtime_checkable
class MessagePort(Protocol):
    """所有需要给用户发消息的地方通过这个接口，不直接调 dingtalk_client"""

    async def send_card(self, user_id: str, card: TDLCard) -> bool: ...
    async def send_markdown(self, user_ids: list[str], title: str, text: str) -> bool: ...
    async def send_interactive_card(self, user_id: str, template_id: str, data: dict) -> bool: ...
```

```python
# contracts/tagger.py —— 标签分类接口

@runtime_checkable
class Tagger(Protocol):
    """模块 2 结构化处理的核心能力"""

    async def extract_fields(self, raw_text: str) -> TDLFieldDraft: ...
    async def classify_tags(self, title: str, context: str) -> TagResult: ...
    async def parse_meeting_minutes(self, text: str) -> MeetingParseResult: ...
```

### 5.3 改动计划

| 步骤 | 内容 | 改动量 |
|------|------|--------|
| 1 | 新建 `app/contracts/` 目录，放三个 Protocol 定义 | ~60 行 |

## 六、第三层：插件化扩展体系

### 6.1 设计总则

插件体系的三个原则：

1. **核心不依赖插件，插件依赖核心**。插件可以调 TDLStore 读数据、可以调 MessagePort 发消息，但不能让核心模块感知插件的存在。
2. **每个插件独立交付、独立验收、独立开关**。一个插件挂了不影响其他插件，更不影响主链路。
3. **插件之间不直接通信**。数据共享通过核心存储层中转，避免插件间网状耦合。

### 6.2 插件接口基约

```python
# contracts/plugin.py

@runtime_checkable
class TDLPlugin(Protocol):
    """所有插件必须实现的接口"""

    # 元信息
    plugin_id: str          # 唯一标识，如 "manager-capability"
    plugin_name: str        # 中文名，如 "管理者能力模型"
    version: str            # 语义版本

    # 生命周期
    async def on_install(self, store: TDLStore) -> None: ...
    async def on_tdl_created(self, tdl: TDL) -> None: ...       # TDL 创建后的钩子
    async def on_tdl_completed(self, tdl: TDL) -> None: ...     # TDL 完成后的钩子
    async def on_tdl_overdue(self, tdl: TDL, days: int) -> None: ...  # TDL 逾期钩子
    async def on_weekly_report(self, report: WeeklyReportRead) -> None: ...  # 周报生成后钩子
    async def get_insights(self, owner_id: str, since: datetime) -> list[Insight]: ...  # 主动查询洞察
```

### 6.3 插件列表（首批 6 个）

| # | 插件 | 阶段 | 说明 |
|---|------|------|------|
| P1 | 管理者能力模型 + 帮扶建议 | 第 2 阶段 | 从 TDL 完成数据中分析管理者行为模式，生成帮扶建议 |
| P2 | 任务结果回收入口 | 第 2 阶段 | TDL 完成后主动回收：结果成败、收益、多方反馈 |
| P3 | 业务线自定义标签 | 第 2 阶段 | 允许各业务线扩展自己的标签维度，不污染核心标签词典 |
| P4 | 周期性项目模板 | 第 2 阶段 | 固化各职能域的周期任务模板，自动生成重复 TDL |
| P5 | 管理战略分析模型 | 第 3 阶段 | 宏观：业务线战略执行健康度、资源分配合理性、跨业务协同效率 |
| P6 | 统筹计划/任务优化模型 | 第 3 阶段 | 中观：多任务排期优化、瓶颈识别、优先级动态调整建议 |

### 6.4 P1：管理者能力模型 + 帮扶建议

#### 做什么

不靠人填写评估表，从 TDL 系统里的行为数据自动生成管理者能力画像。数据来源：

- 完成率趋势（周/月）
- 逾期率、逾期严重程度
- 卡在什么类型任务上（按职能域/关键动作分类）
- 暂缓频率和原因模式
- 协作模式（waiting_for 的频次和对象）
- 应对追问的行为（延期 vs 完成 vs 求助的倾向）

#### 能力维度

| 维度 | 数据指标 | 洞察方向 |
|------|---------|---------|
| 执行闭环力 | 完成率、逾期率、草稿确认及时性 | 是否"说了就做、做完有回音" |
| 时间管理力 | 逾期严重度趋势、暂缓频率、deadline 修改次数 | 是否能准确预估工作量 |
| 问题解决力 | 求助频率、阻塞 TDL 占比、阻塞原因分布 | 遇到卡点是推动解决还是被动等待 |
| 任务拆解力 | 父任务/子任务比例、大任务平均完成周期 | 是否能将复杂任务拆成可执行步骤 |
| 协作联动 | waiting_for 频率与对象、跨职能域 TDL 占比 | 是否只埋头自己的事、跨部门协作是否顺畅 |

#### 帮扶建议生成规则（示例）

```
IF 逾期率连续 2 周 > 30% AND 暂缓次数 > 3:
    → 建议：「近两周任务积压较重，建议做一次待办瘦身——标记哪些可取消、哪些可委派」

IF 阻塞 TDL 中 waiting_for 占比 > 60%:
    → 建议：「当前大部分阻塞在等他人反馈，建议指定明确的回复截止时间，或主动同步进度」

IF 特定职能域逾期集中:
    → 建议：「教学类 TDL 逾期率明显高于其他，是否需要教务侧流程支持？」
```

#### 帮扶建议的输出形式

每周周报末尾附带一句个性化建议（纯数据驱动，不做评判）。月度复盘会前生成一份完整的成长档案快照。

**注意**：帮扶建议是给少巍和李珍看的（作为辅导参考），默认不推给管理者本人。是否推、推什么内容，后续根据实际使用情况决定。

### 6.5 P2：任务结果回收入口

#### 做什么

当前 TDL 生命周期以"已完成"为终点。但实际上，完成质量和产生的影响才是管理价值的来源。P2 在 TDL 完成后打开一个回收入口，让执行者补充三类信息：

#### 回收字段

| 字段 | 说明 | 示例 | 必填 |
|------|------|------|------|
| `outcome_result` | 最终结果 | 成功 / 部分达成 / 未达成 | 是 |
| `outcome_benefit` | 收益描述 | "续费率从 72% 提升到 78%" | 否 |
| `outcome_benefit_level` | 收益量级 | 高 / 中 / 低 | 否 |
| `feedback_employee` | 底层员工反馈 | "班主任反馈新流程减少了 30% 重复沟通" | 否 |
| `feedback_parent` | 家长端反馈 | "家长群对新的课后反馈模板评价积极" | 否 |
| `feedback_market` | 市场端反馈 | "抖音线索质量比上月提升" | 否 |
| `outcome_note` | 自由备注 | 任何想记录的收获和教训 | 否 |

#### 交互方式

TDL 标记完成后，系统发一张轻量回收卡片：

```
┌────────────────────────────────────────┐
│ ✅ 已完成：励步暑期招生方案终稿           │
│                                        │
│ 做得好，再花 30 秒做个记录？              │
│                                        │
│ 结果：[○ 成功  ○ 部分达成  ○ 未达成]     │
│ 收益：[____________]                    │
│ 反馈：[📝 补充反馈]                      │
│                                        │
│ [💾 保存] [跳过]                       │
└────────────────────────────────────────┘
```

如果用户跳过，24 小时内再问一次。两次跳过则该 TDL 关闭回收通道。

#### 数据流向

回收数据写入 `tdls` 表的 5 个预留字段（`outcome_kpi` 复用为结构化结果，新增 3 个 feedback 字段和 `outcome_benefit_level`）。这些数据是 P1 管理者能力模型和 P5 管理战略分析模型的输入源。

### 6.6 P3：业务线自定义标签

#### 做什么

核心标签词典（02 号文档 §三）是全局统一的基础分类。但各业务线有自己的特色维度：

- **励步英语**：K/G/SS 阶段标签细分、续费节点标签、新师成熟度阶段标签
- **斯坦星球**：STEM/CODE/PythonAI/C++ 产品线细分、赛事等级标签
- **飞书工资**：需求类型标签（功能新增/缺陷修复/性能优化）、客户优先级标签

这些标签不应该塞进核心标签词典（会被 AI 拿来跨业务线乱分），而应该作为插件挂在各业务线上。

#### 实现方式

每新增一个业务线自定义标签文件（如 `plugins/tags/libu_custom_tags.yaml`），插件读取后只在 TDL 的 `business_line` 匹配时才应用这些标签。不影响其他业务线的分类。

### 6.7 P4：周期性项目模板

#### 做什么

02 号文档 §2.6 已经提取了各部门的周期任务模板（教务每周听课覆盖、教学每月续费跟盯、HR 每周招聘推进等）。P4 把这份模板从文档变成可执行的自动化：

- 模板启用后，按周期自动生成 TDL 草稿
- 负责人确认后进入正常 TDL 流转
- 模板缺位检测（第 2 阶段末）：如果某部门连续 N 周没有生成对应周期 TDL，系统提示"是否遗漏了例行工作"

#### 模板定义文件

`plugins/templates/cadence_templates.yaml`，从现有 02 号文档直接转化。

### 6.8 P5：管理战略分析模型（宏观）

#### 定位

面向少巍和李珍的战略层分析工具。不同于周报（运营级事实统计），P5 回答的是**整体性的管理问题**：

- 各业务线的战略执行健康度如何？（从任务完成率、阻塞集中度、关键动作覆盖度综合判断）
- 资源分配是否合理？（当前各职能域 TDL 密度分布、是否存在某些职能域长期积压）
- 跨业务协同效率？（励步/斯坦之间协作 TDL 的完成周期 vs 单业务 TDL）
- 从任务数据反推组织瓶颈？（哪个环节长期是卡点）

#### 数据输入

- TDL 全量数据（按业务线、职能域、关键动作、优先级多维度聚合）
- P2 任务结果回收数据（成败率、收益分布、反馈倾向）
- P1 管理者能力维度评分（按职能域聚合）

#### 输出形式

月度复盘会前，生成一份「月度战略健康报告」：
- 各业务线执行健康度评分（A/B/C 三级）
- 资源分配热力图（业务线 × 职能域的 TDL 密度）
- 阻塞趋势图（哪些环节的 TDL 阻塞率在上升）
- 跨业务协同健康度
- 建议关注的 3 个关键事项

这份报告不替代人的判断，而是提供事实基座——让月度复盘会上的讨论有数据依据，而不是凭印象。

### 6.9 P6：统筹计划/任务优化模型（中观）

#### 定位

面向单个管理者的任务排期优化。不同于 P5 的宏观分析，P6 回答的是**操作级的效率问题**：

- 「本周有 8 条 TDL，建议的处理顺序是什么？」
- 「这条 P0 任务按目前进度可能逾期，建议提前做什么？」
- 「张蕾名下同时有 12 条进行中的 TDL，其中 4 条在等他人反馈、3 条已逾期——优化方案是什么？」

#### 核心能力

**优先级动态重排**：不是创建时标一次 P0-P3 就不再调整。P6 根据截止时间临近度、阻塞状态变化、上下游依赖关系，动态建议调整优先级。

**瓶颈预测**：当某管理者的进行中 TDL 超过阈值（如 10 条），且逾期率上升，系统预判"可能即将积压"并提前建议瘦身。

**依赖链分析**：当 TDL A 被 TDL B 阻塞、B 又依赖 C 时，P6 画出阻塞链路，建议从链尾开始逐个击破。

#### 输出形式

- 每日提醒卡片里附带一句优先级建议
- 每周一推一张简版"本周建议处理顺序"
- 被追问时（"我现在该先做什么"）返回排序建议

## 八、Codex 开发指引

### 8.1 每个模块完工的定义

从「代码写完了」到「模块确认交付」，Codex 需要完成四件事：

| # | 事项 | 说明 |
|---|------|------|
| A | 代码实现 | 功能代码 + 单元测试 |
| B | 接口契约检查 | 确认模块只 import 了允许的接口，没有越权调用其他模块的实现 |
| C | 离线验收通过 | 按 4.2 节的验收标准逐项跑通，不依赖完整钉钉环境 |
| D | 验收报告 | 一份简短的 markdown 报告，列出：通过了哪些验收项 / 哪些项未通过及原因 / 已知局限 |

### 8.2 不让 Claude 审什么

Claude 的 review 范围不变（按 SOP 10），但明确 Claude 不需要审的内容：

- 插件内部实现细节（插件是独立交付单元，出问题不影响主链路）
- 验收报告里的数据（这些由 Codex 自己保证准确性）
- 仅限 `app/contracts/` 的接口变更——接口变更必须审，因为它影响所有消费者

### 8.3 插件开发顺序

```
P3（业务线标签）  →  P4（周期模板）  →  P2（结果回收）  →  P1（能力模型）  →  P6（统筹优化）  →  P5（战略分析）
   最轻量              有模板可转化        需要 UI 交互        依赖积累数据         依赖 P1 数据        依赖 P1+P2 数据
```

理由：先做不依赖数据的插件（P3/P4），积累数据后再做需要数据的插件（P1/P5/P6），避免"分析模型建好了但没有数据"的尴尬。

### 8.4 新增模块/插件时的检查清单

Codex 新增任何模块或插件前，必须确认：

- [ ] 新模块的接口契约已定义在 `contracts/` 下
- [ ] 新模块不 import 任何其他模块的实现文件（只 import 接口）
- [ ] 新模块的离线验收用例已写好（在 `tests/contracts/` 下）
- [ ] 与现有模块的集成点已标注在依赖地图上
- [ ] 如果新增数据库字段，已通过 Alembic 迁移且向下兼容
