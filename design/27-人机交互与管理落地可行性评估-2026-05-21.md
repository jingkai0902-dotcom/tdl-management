# 27 · 人机交互与管理落地可行性评估 — 2026-05-21

## 一、本文定位

本文记录 Anti-Gravity 对 TDL 管理交互系统提出的人机交互与管理落地建议，以及 Claude、Codex 对这些建议的交叉评估和采纳分级。

本文只处理 UX / HCI / 管理落地问题，不改变 `26-架构蓝图建议评估与分阶段采纳-2026-05-21.md` 中已经确认的架构边界。尤其是：

1. 不新增知识层正式表。
2. 不提前实现 OKR / KR。
3. 不把会议材料批量创建为正式 TDL。
4. 不把交互体验建议扩大成经营插件开发。

本文与 `25-任务卡与多任务通知体验规划-2026-05-20.md` 的关系是：25 号定义任务卡与多任务通知的现有体验路线，本文补充 Anti-Gravity 这轮 UX 建议的采纳优先级。

## 二、总体判断

Anti-Gravity 这轮建议明显比第一轮架构蓝图更贴近当前试点。六个建议都围绕卡片、提醒、会议任务确认、完成反馈等真实交互，没有要求立即建知识图谱、拆多运行时或做上层经营插件。

三方共识：

| 建议 | 采纳级别 | 当前结论 |
|---|---|---|
| 草稿卡片底部修正引导语 | 近期采纳 | 成本低，能直接暴露 PR #74 / #77 已具备的 follow-up 纠错能力 |
| 会议任务聚合确认卡 | 阶段 2 / 会议录入 | 与 25 号聚合卡方向一致，按负责人分组更贴近用户心智 |
| 模糊截止期 | 阶段 3 | 洞察正确，但涉及数据模型、日历策略和提醒策略，不进入当前 PR-E |
| 逾期提醒重谈判 / 今天别吵我 | 近期采纳部分能力 | 系统已有延期、暂缓、求助；新增价值主要是“不改 due_at 的明早再提醒” |
| 证据链与上下文指派人展示 | 近期采纳材料来源任务 | 低成本高信任价值，但只适用于会议 / 材料来源任务 |
| 标记完成后的结果回收 | 阶段 2 | 有价值，但必须可跳过、低频、优先用于高价值任务 |

## 三、近期采纳项

### 1. 草稿卡片增加 follow-up 修正引导语

当前后端已经支持对草稿或近期 active TDL 进行 follow-up 纠错，包括负责人、截止时间和完成标准修正。但用户并不知道可以直接回复自然语言修正。

近期建议：

在草稿卡片底部增加一行轻提示，例如：

```text
可直接回复“改成李珍”“时间改到下周五”“完成标准是形成一页结论”来修正。
```

边界：

1. 只作为提示语，不新增复杂交互。
2. 不替代按钮，按钮仍保留。
3. 文案必须短，避免把卡片变成说明书。
4. 语音输入同样适用，因为钉钉会先转文字。

价值：

1. 把已经实现的 follow-up 纠错能力暴露给用户。
2. 降低移动场景下精准点击按钮的负担。
3. 减少“用户以为只能点按钮”的心智误差。

### 2. 材料来源任务展示 speaker / evidence_span / 指派上下文

会议或材料来源的 TDL 草稿如果只展示任务名、负责人和截止时间，用户很难判断这是明确指派、讨论火花，还是 AI 深加工出来的伪决议。

近期建议：

对会议 / 材料来源任务，在卡片中展示最小证据链：

| 字段 | 说明 |
|---|---|
| `source_title` | 来源会议或材料名称 |
| `speaker_name` | 原始发言人或指派人 |
| `speaker_role` | 发言人当时岗位 / 职责 |
| `evidence_span` | 原文证据片段 |

边界：

1. 只适用于会议 / 材料来源任务。
2. 日常语音或文字录入没有 `speaker` 和 `evidence_span`，不能为了统一卡片强行补假上下文。
3. 展示原文证据时要短，优先展示最能证明 `What + Who + When` 的片段。
4. 如果证据链缺失，该任务不应作为可直接确认的会议 TDL。

价值：

1. 降低“熟悉又陌生”的错位感。
2. 让负责人知道“是谁在什么上下文里提出的”。
3. 支撑会议伪决议拦截，而不是只在离线 gold set 中保留证据。

### 3. 逾期提醒增加“今天别吵我 / 明早再提醒”

当前系统已经有 `snooze`、`postpone`、`need_help` 等能力。Anti-Gravity 提出的逾期提醒心理学优化中，最有增量价值的是一个不改变 `due_at` 的短期免打扰动作。

近期建议：

在逾期或今日提醒卡中增加类似按钮：

```text
今天别吵我
```

或：

```text
明早再提醒
```

边界：

1. 这是提醒层面的 snooze，不是任务延期。
2. 不修改任务原始 `due_at`。
3. 不降低任务状态严肃性，只是减少当天重复打扰。
4. 默认 snooze 到下一工作日上午，而不是让用户必须输入时间。

价值：

1. 给用户一个低成本出口，避免逾期提醒造成回避心理。
2. 区分“我需要安静一下”和“我承诺新截止时间”。
3. 复用现有 `snooze` 方向，改动范围可控。

## 四、阶段 2 采纳项

### 1. 会议任务聚合确认卡

会议自动提取任务时，不应把 6 到 12 张卡片逐条刷给同一个用户。25 号文档已经明确批量会议任务应使用聚合摘要卡。

本轮补充采纳：

1. 聚合卡优先按负责人分组。
2. 每个负责人组内再按优先级和截止时间排序。
3. 卡片应展示“可直接创建 / 待补字段 / 进入议题池”的数量。
4. `全部创建` 只适用于 owner、due_at、completion_criteria 完整的任务。
5. `全部忽略` 需要二次确认或限制在测试阶段。

原因：

负责人更关心“我被分配了什么”，而不是系统内部优先级列表。按负责人分组比单纯按 P0/P1/P2 更贴近管理者心智。

### 2. 标记完成后的轻量结果回收

完成任务后的结果回收有价值，因为它能把 `Task` 逐步连接到真实经营事实。但当前不能把每次完成都变成追问，否则会增加负担。

阶段 2 建议：

1. 完成后可选追问一句：“有关键结果或输出物吗？可直接回复文字/语音，或点跳过。”
2. 默认允许跳过。
3. 优先只对高价值任务、会议明确事项或 owner 主动补充的任务开启。
4. 第一阶段只记录结果文本，不自动写入正式 `Fact` 表。
5. 等知识层进入阶段 3 后，再评估从结果文本中抽取 `Fact / Metric / Signal`。

边界：

1. 不强制回收。
2. 不把“完成”按钮变成新的工作负担。
3. 不在知识层正式建表前承诺自动沉淀经营事实。

## 五、阶段 3 采纳项

### 模糊截止期与日历污染防御

Anti-Gravity 对“下周内 / 本月内”被 AI 硬补成某天某点的风险判断是正确的。强行把模糊时间写成精确 `datetime` 会污染日历，也会让用户误以为系统替自己做了时间承诺。

当前处理原则：

1. 不满足明确 `When` 的会议内容，不进入 confirmed TDL。
2. 日常录入中如果时间模糊，优先追问或保持草稿待补。
3. 当前不新增 `due_at_type`。

阶段 3 再评估：

| 类型 | 示例 | 日历策略 |
|---|---|---|
| `precise` | 5 月 23 日 18:00 | 可写日历 |
| `date` | 5 月 23 日 | 视提醒策略写全天或默认时间 |
| `week` | 下周内 | 不直接写个人日历，进入周概览 |
| `month` | 本月内 | 不直接写个人日历，进入月度目标 / 任务池 |
| `tbd` | 时间待定 | 草稿待补或议题池 |

## 六、当前不采纳为开发项

以下内容不进入当前 PR-E 代码开发：

1. 会议聚合卡的一键批量创建正式生产任务。
2. `due_at_type` 字段或日历策略迁移。
3. 完成后自动写入正式 `Fact / Metric / Signal`。
4. 对所有完成任务强制结果回收。
5. 对日常录入卡片强行展示不存在的 speaker / evidence_span。
6. 任何基于交互数据的管理者评分或画像。

## 七、对 PR-E 和 25 号文档的影响

PR-E 体验候选中，建议新增或前移：

1. 草稿卡片 follow-up 修正引导语。
2. 材料来源任务证据链展示。
3. 逾期 / 今日提醒的“今天别吵我 / 明早再提醒”按钮。

25 号文档的聚合卡方向保持不变，但后续实现会议聚合卡时，应采用：

```text
按负责人分组 + 组内按优先级 / 截止时间排序
```

26 号文档的架构采纳口径保持不变。27 号只补充 UX/HCI 层面的落地分级，不覆盖 26 号。
