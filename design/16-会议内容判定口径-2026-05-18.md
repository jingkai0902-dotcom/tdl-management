# 16 · 会议内容判定口径 — 2026-05-18

## 一、最高原则

TDL 系统宁可漏提，也不能把“说过、想过、倡导过”误判为“已经决定要执行”。

原因：

1. TDL 的核心资产不是任务数量，而是用户信任。
2. 一旦管理者收到一个自己并不认可为“已决定执行”的提醒，就会怀疑系统是否在替会议做结论。
3. 这种信任损失会沿着整个链路扩散到：
   - 草稿确认
   - 提醒
   - 逾期追踪
   - 周报
   - 后续会议录入

因此，会议录入必须默认采用**最严苛判定**。

## 二、一级分类

| 类别 | 定义 | 是否可直接转 TDL |
|---|---|---|
| `事实` | 已发生或当前已存在的客观内容 | 否 |
| `已明确事项` | 已达到可执行阈值的内容 | 可以 |
| `待处理议题` | 被讨论过，但尚未形成可执行安排 | 否 |
| `火花/设想` | 愿望、倡导、方向感、初步想法、值得保留但尚未成熟的内容 | 否 |
| `观察线索` | 暴露出的现象、风险、机会或值得继续看的苗头 | 否 |

## 三、“已明确事项”的最严苛标准

除纯客观事实外，只有同时满足以下 3 项，才允许标为 `已明确事项`：

1. `What`：要做什么已经明确。
2. `Who`：由谁负责已经明确。
3. `When`：已经明确开始时间或完成时间之一。

补充说明：

- `Where` 仅在事项本身依赖地点时才要求。
- `How` / `Output` 若已明确，可提升任务质量，但不是最低门槛。
- 只有 `What`，没有 `Who` 和 `When`，一律不能进 `已明确事项`。
- 只有方向、愿望、倡导、口号、目标陈述，一律不能进 `已明确事项`。

## 四、内容成熟度与对象类型分离

会议内容要同时回答两个问题：

1. **成熟到哪一步了**
2. **它本质上是什么**

### 1. 成熟度

| 成熟度 | 说明 |
|---|---|
| `fact` | 已发生 / 已存在 |
| `confirmed` | 达到 `What + Who + When` |
| `pending` | 已进入讨论，但未达执行阈值 |
| `spark` | 仍是设想、愿望、倡导或方向感 |
| `signal` | 只是观察到的苗头 |

### 2. 对象类型

| 类型 | 说明 |
|---|---|
| `Fact` | 事实 |
| `Decision` | 判断 |
| `Task` | 动作 |
| `Issue` | 待处理问题 |
| `Idea` | 火花、设想 |
| `Signal` | 观察线索 |

一个对象必须同时带：

- `maturity`
- `object_type`

例如：

- `管理者要 AI first` = `spark + Idea`
- `薪资多维表格已试运行一次` = `fact + Fact`
- `前端字段由 X 于 5 月 20 日前整理` = `confirmed + Task`

## 五、严格边界示例

| 原始内容 | 正确分类 | 错误分类 |
|---|---|---|
| “以后大家要多用 AI” | `spark + Idea` | `confirmed + Task` |
| “10 月底要实现单校区健康运行” | `pending / Goal` 或 `spark / Idea`，取决于上下文 | `confirmed + Decision` |
| “薪资表这月已经试运行一次” | `fact + Fact` | `Decision` |
| “前端先列数据维度，后端列承接字段，之后再由 Frank 梳理逻辑” | 如果已明确负责人和时间，则 `confirmed + Task`；否则 `pending + Issue` | 自动当成任务 |
| “Walk-in 转化很差” | `fact + Fact` 或 `signal + Signal` | 直接派生“优化 Walk-in 转化”任务 |

## 六、系统行为要求

### 1. 对 `confirmed`

- 可以进入 TDL 草稿池。
- 仍需保留原始证据和来源。
- 如果字段不全，只能生成草稿，不得自动补造。

### 2. 对 `pending`

- 进入议题池。
- 可以提醒“下次会议继续讨论”。
- 不得直接给责任人发执行提醒。

### 3. 对 `spark`

- 进入火花池。
- 可设置回看提醒。
- 不得伪装成计划或决议。

### 4. 对 `signal`

- 进入观察池。
- 可与后续数据、会议、系统事实交叉验证。
- 未经后续确认，不得自动升级成任务。

## 七、后续研究方向

后续还需要继续深入研究：

1. 是否把 `Goal` 单列为独立对象，而不是混在 `Decision / Idea` 之间。
2. 如何区分：
   - `方向明确`
   - `判断明确`
   - `执行明确`
3. `pending` 议题在什么条件下可以升级为 `confirmed`。
4. `spark` 经过多久、满足什么证据后，可以升级为 `Issue`。
5. 如何在钉钉界面里让用户一眼看懂：
   - 这是任务
   - 这是待议题
   - 这是火花
   - 这是观察线索

## 八、当前决议

2026-05-18，确认采用**最严苛版本**：

> 除客观事实外，只有同时满足 `What + Who + When` 的内容，才允许进入 `已明确事项`。

这是后续会议录入、日常讨论沉淀、TDL 流转和所有插件能力的共同底线。
