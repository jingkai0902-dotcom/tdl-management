# 25 · 任务卡与多任务通知体验规划 — 2026-05-20

## 一、本文结论

日常 TDL 助手后续的交互体验优化，不应追求“所有任务都发卡片、所有卡片都原位刷新”。合理方向是：

1. 单条日常任务继续使用单任务卡。
2. 批量会议任务使用聚合摘要卡，避免卡片轰炸。
3. 点击后的可靠反馈优先于原卡视觉变化。
4. 原卡替换可以实验，但不能替代当前已验证的反馈消息兜底。

当前钉钉模板卡的现实约束已经明确：按钮点击后原卡灰态、按钮消失、原位变成“已处理”，本轮实测未打通。系统应把它视为 P1 体验专项，而不是 P0 主链路条件。

## 二、外部经验的可借鉴原则

本节只提炼可落地原则，不引入外部系统。

### 2.1 通知必须有上下文

Slack 的官方应用设计指南强调，消息应直接、简洁、可操作，并给用户必要上下文。映射到 TDL：按钮反馈不能只写“已完成”，应写明是哪条任务、处理后会发生什么。

当前已落地：

```text
已标记完成
「完成 Codex A1 标记完成测试」已完成，不再提醒
```

### 2.2 降低通知疲劳

协作工具的通用经验是减少不必要的打扰，把相关事项合并到更少、更有结构的通知里。映射到 TDL：日常 1-3 条可以单卡，会议后 8-10 条不能逐条刷屏。

### 2.3 卡片动作必须有可靠确认

钉钉按钮点击后的原生小圈不足以让用户确认状态。当前系统用单独工作通知做确认，这是现阶段最可靠方案。后续如果试验原卡替换，也必须保留反馈消息兜底。

## 三、场景分流

| 场景 | 推荐形态 | 理由 |
|---|---|---|
| 日常单条录入 | 单任务卡 | 最短路径，用户能直接确认、暂缓、完成或拒绝 |
| 日常 2-3 条连续录入 | 仍用单任务卡 | 数量低，不值得增加聚合复杂度 |
| 每日提醒（同人同批次） | 提醒聚合卡 | 08:30 扫出多条 overdue/due 时，合并为一次早晨提醒，避免同一用户连续收到 3-5 张卡 |
| 会议录入批量产出 | 聚合摘要卡 + 后续逐条处理 | 避免 8-10 张卡片轰炸 |
| 逾期提醒 | 单任务提醒卡 | 每条任务需要独立决策 |
| 需补字段草稿 | 单任务卡或聚合摘要里的“待补字段”区 | 补字段通常需要自然语言追加，不适合批量一键 |

### P1：下一轮体验实验

1. `outTrackId` 卡片替换实验。
   - 目标：点击按钮后尝试用同一 `outTrackId` 发一张结果卡，观察是否替换原卡。
   - 成功标准：用户侧原卡位置出现“已处理/已完成/已暂缓”结果卡。
   - 失败处理：不回退现有反馈消息；记录钉钉平台限制。
   - 范围：单独 PR，单独真实钉钉验证。

2. 每日提醒聚合卡。
   - 目标：同一轮 APScheduler 提醒中，同一 owner 的多条 overdue/due 任务合并为一张早晨提醒卡。
   - 数据源：reminder cycle，而不是 meeting parse。
   - 卡片内容：按“逾期 / 今日到期 / 暂缓到期”分组，展示任务标题、截止时间和优先级。
   - 动作设计：优先提供“查看逐条卡片 / 打开助手处理”，不要在第一版做批量完成或批量拒绝。
   - 兜底：P0 或单条紧急任务仍可单独提醒，不被聚合吞掉。

3. 按钮初始样式和层级。
   - 主动作：蓝色，例如 `确认创建`、`标记完成`。
   - 次动作/负向动作：普通样式，例如 `忽略`、`不是我的任务`。
   - 前提：需要确认钉钉模板是否能按按钮槽位设置不同静态样式。

4. A1 反馈复测。
   - A1 后端已成功，但首次未收到反馈。
   - PR #70 后 A2/A3 反馈已到达，仍应补一次 A1 新版反馈复测。

### PR-E / 会议录入阶段

1. 批量聚合卡。
   - 同一会议、同一批次、已明确事项聚合成一张摘要卡。
   - 按优先级、截止时间、负责人分组。
   - 明确展示“已明确事项”和“进入议题池/待补字段”的数量。

2. 聚合卡动作设计。
   - `逐条确认`：进入助手私聊或逐条卡片流。
   - `全部创建`：只适用于 owner、due_at、completion_criteria 都完整的草稿。
   - `全部忽略`：需要二次确认或仅限测试阶段，避免误删真实会议产出。

3. TokenJuice 类预处理。
   - 对会议材料先做去重、格式归一、相似段落合并，再进入分类 pipeline。
   - 目标是降低 token 成本，同时减少模型被重复材料干扰。

### 推广前

1. 通知频控。
   - 同一用户短时间内多条反馈是否需要合并。
   - 在每日提醒聚合卡跑通后，再评估是否需要更细的频控策略。

2. 每日摘要。
   - 定位为经营回顾和趋势摘要，而不是当前试点的早晨任务提醒。
   - 不替代 P1 的每日提醒聚合卡，也不替代关键 P0 提醒。

3. 入口问题 R5。
   - 2026-05-20 复测仍跳广告页，不稳定回到助手私聊。
   - 当前先把“继续处理请回到 TDL 助手私聊。”写入反馈消息兜底。
   - 后续再查钉钉后台应用入口配置。

## 五、暂不做

1. 不引入 OpenHuman。
   - 当前系统是组织级 TDL 管理，不是个人桌面 agent。
   - GPL-3.0 与商业化方向不友好。

2. 不拆 6 个通用 Skill。
   - 当前已有 AGENTS.md、tdl-live-ops、PR review SOP 和自动化测试。
   - 先把 `Testing focus` 纳入 PR 模板，比新建 test engineer skill 更轻。

3. 不在当前阶段做 12-agent 编排。
   - 当前瓶颈是真实链路和试点反馈，不是 agent 数量。

## 六、判断标准

后续体验优化是否有效，不看界面是否“更像高级产品”，看四个结果：

1. 用户点击后 5 秒内能明确知道是否成功。
2. 用户不需要回看原卡，也能知道处理的是哪条任务。
3. 批量会议任务不会造成钉钉卡片轰炸。
4. 任何实验失败时，不影响现有状态写回和反馈消息兜底。
