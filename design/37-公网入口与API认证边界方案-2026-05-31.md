# 37 · 公网入口与 API 认证边界方案 - 2026-05-31

## 一、本文结论

TDL 当前最大的系统安全缺口不是某一个按钮，而是 HTTP 入口缺少统一边界。

下一轮扩大试用前，应先完成一个最小认证与入口隔离 PR 序列：

1. 公网只暴露必要页面和 OAuth callback。
2. 写入类、调试类、运维类 API 默认不向公网开放。
3. 内部 API 增加统一 `X-TDL-Internal-Key` 认证依赖，作为 Nginx allowlist 之外的第二道防线。
4. 工作台 V0 继续默认关闭；正式启用前不把 `owner_id` 当身份。

这不是上层功能开发，而是恢复开发前的安全底座。

## 二、当前事实

当前 `app/main.py` 默认注册：

| 路由组 | 当前状态 | 风险 |
|---|---|---|
| `/`、`/entry` | 入口页 | 可公网展示，低风险 |
| `/health` | DB health | 可用于监控，但会暴露 DB connected 状态 |
| `/calendar/auth/start` | 日历授权开始 | 可被构造 user_id 触发授权跳转 |
| `/calendar/auth/callback` | 钉钉 OAuth callback | 需要公网可访问 |
| `/tdls` | TDL 创建/列表 | 写入/读取 API，无认证 |
| `/dingtalk/messages` | HTTP intake 测试入口 | 可创建草稿，无认证 |
| `/dingtalk/actions/*` | HTTP 动作入口 | 可确认、完成、暂缓、拒绝，无认证 |
| `/meetings/*` | 会议 ingest / parse / results | 可写会议和触发 AI 解析，无认证 |
| `/reminders/run` | 手动提醒周期 | 可触发提醒状态变化和发送链路 |
| `/reports/weekly` | 周报生成 | 可读取管理汇总 |
| `/workbench/*` | 只读工作台 V0 | 默认关闭，启用后无身份认证 |

当前 Nginx 片段是整体代理 `/tdl/` 到 backend，没有按路径区分公网与内部入口。

## 三、路由分级

### A 类：允许公网访问

| 路径 | 条件 | 说明 |
|---|---|---|
| `/`、`/entry` | 可公网 | 只展示入口说明，不写数据 |
| `/health` | 可公网或内网监控 | 只返回健康状态；如不需要公网监控，也可改内网 |
| `/calendar/auth/callback` | 必须公网 | 钉钉 OAuth 回调需要访问 |

### B 类：受限公网访问

| 路径 | 建议 | 说明 |
|---|---|---|
| `/calendar/auth/start` | 只允许系统生成的短期链接访问 | 当前只有 user_id 参数，建议加一次性 nonce 或内部签名 |
| `/workbench/*` | 试点期仅本机/内网；正式启用前接身份 | `owner_id` 只能做视角筛选，不能做身份 |

### C 类：内部 API，默认不得公网访问

| 路径 | 保护方式 |
|---|---|
| `/tdls` | Nginx 阻断公网 + 内部 API key |
| `/dingtalk/messages` | Nginx 阻断公网 + 内部 API key |
| `/dingtalk/actions/*` | Nginx 阻断公网 + 内部 API key |
| `/meetings/*` | Nginx 阻断公网 + 内部 API key |
| `/reminders/run` | Nginx 阻断公网 + 内部 API key |
| `/reports/weekly` | Nginx 阻断公网 + 内部 API key |

## 四、最小实现方案

### 4.1 配置

新增：

```text
INTERNAL_API_KEY=
```

规则：

1. 生产环境必须配置。
2. 本地开发可为空；为空时仅在 `APP_ENV=development` 允许跳过。
3. 不把 key 写入日志、状态文件、文档或测试输出。

### 4.2 FastAPI 依赖

新增模块：

```text
app/api/auth.py
```

提供：

```python
require_internal_api_key(request: Request) -> None
```

检查：

1. Header `X-TDL-Internal-Key` 是否存在。
2. 使用 `hmac.compare_digest` 做常量时间比较。
3. 未配置生产 key 时启动或请求失败。

### 4.3 保护哪些路由

第一版保护：

1. `tdl_crud.router`
2. `dingtalk_webhook.router`
3. `meetings.router`
4. `reminders.router`
5. `reports.router`

工作台先不接内部 key，因为它是页面入口；继续由 `WORKBENCH_V0_ENABLED=false` 默认关闭。正式工作台另做身份方案。

### 4.4 Nginx 边界

建议把当前整体代理改成“默认拒绝 + 显式允许”。

示意：

```nginx
location = /tdl/ {
    proxy_pass http://127.0.0.1:8010/;
}

location = /tdl/entry {
    proxy_pass http://127.0.0.1:8010/entry;
}

location = /tdl/health {
    proxy_pass http://127.0.0.1:8010/health;
}

location = /tdl/calendar/auth/callback {
    proxy_pass http://127.0.0.1:8010/calendar/auth/callback;
}

location /tdl/ {
    return 403;
}
```

如果确实需要从外部调试内部 API，应临时开 VPN / allowlist，不把内部 key 当成唯一防线。

## 五、测试要求

必须新增测试：

1. 未带 `X-TDL-Internal-Key` 请求受保护 API 返回 401 或 403。
2. 错误 key 返回 403。
3. 正确 key 可访问。
4. `APP_ENV=production` 且未配置 key 时拒绝。
5. `/calendar/auth/callback` 不受内部 key 影响。
6. `/`、`/entry` 不受内部 key 影响。

## 六、不做范围

本方案不做：

1. 完整用户登录系统。
2. 工作台正式权限模型。
3. 钉钉 SSO。
4. 多角色 RBAC。
5. 审计后台。

这些属于后续工作台正式化阶段，不应阻塞当前最小安全闭环。
