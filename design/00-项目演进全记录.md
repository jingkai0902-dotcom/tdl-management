# 00-项目演进全记录 · TDL 管理交互系统

> 本文记录 TDL 管理交互系统从立项到开发全过程的思考演进、方法论借鉴、关键决策、中间调整和困惑解决。
> 未来持续更新。未来开发其他项目时，可从这里提取可复用的框架、流程、方法论。

## 一、项目起源

### 1.1 表层问题

少巍管理两条公司业务（励步英语、斯坦星球）和一条自研技术线（飞书工资系统等 AI 开发项目）。管理层约 15 人，分布在投资人、校区校长、教务主管、教学主管、人力经理、销售/市场经理等角色上。

日常待办的来源包括：月度薪资数据汇总与发放、每周教学磨课、新人过课与授课水平确认、课后总结信息图与备课指南 PDF 的生产、AI 项目的持续开发。

### 1.2 深层问题

> "好的公司，要为组织打造系统的结构能力。一个好的管理系统在于：流程清晰、管理有节奏、决策可落地、落地能回收、回收有效果。"

以前这些靠具体的人来把控。但实际业务中，由于各人主动性差异、能力水平差异、注意带宽差异，很多管理动作掣肘，效能大打折扣。

TDL 作为工具，本可以统筹管理动作的流转和质量，潜移默化提升个人管理水平。但问题在于：它还是会落到个人的差异性上——让 TDL 本身的执行落地难以持续和有质量，经常流于形式，徒增工作负担。

### 1.3 业务一线反馈（李珍视角，系统需求的直接来源）

1. **会议无闭环**：会议上发现的问题、决议、未决事项，没有稳定留痕和追踪轨迹
2. **执行走形难发现**：管理者会后是否执行、执行到哪、是否走形，缺少固定反馈机制
3. **TDL 太重**：现有模板结构完整但管理者难以长期坚持
4. **管理者能力短板**：普遍在目标拆解、复盘、规划、深度思考上有短板
5. **辅导后变形**：辅导后"当场听懂，回去变形或忘记"
6. **月度断线**：月会间隔太长，上个月决议到下个月容易断线
7. **老板盯不住**：少巍事务多，靠自己盯重点只能坚持两三周
8. **需要串起来**：需要 AI 把会议、任务、责任人、反馈、复盘、管理者成长、老板督办串成一个闭环
9. **信息通道缺失**：李珍与教学部之间缺乏结构化汇报路径

## 二、方法论与框架借鉴

### 2.1 GTD（Getting Things Done）—— 核心业务框架

**来源**：David Allen 的时间管理方法论

**借鉴方式**：GTD 五步流程（Capture → Clarify → Organize → Engage → Reflect）直接映射为 TDL 系统的五个功能模块：

| GTD 步骤 | TDL 系统模块 |
|----------|------------|
| Capture 捕获 | 意图捕获（记下来） |
| Clarify + Organize 厘清+组织 | 结构化处理（理清楚） |
| Engage 执行 | 进度推进（推得动） |
| Reflect 反思 | 复盘可见（看得见） |
| —（组织层面延伸） | 沉淀进化（长出来） |

**借鉴程度**：框架级别。GTD 提供了业务流程的完整性保障——确保从"想到"到"做到"到"回头看"的每一步都有系统承载。

### 2.2 《天道》农户制作音箱模式 —— 架构思维启发

**来源**：电视剧《天道》（原著《遥远的救世主》），丁元英组织王庙村农户制作音箱

**核心模式**：各环节商户独立负责、权责清晰、独立交付、互不深度绑定

**借鉴方式**：启发少巍思考"积木式模块化拼搭架构"——每个模块独立负责、可独立交付，避免做成耦合度高的线性整体

**实际落地**：经过与技术现实的校准，从"微服务独立部署"调整为"模块化单体 + 接口契约层"——保留了独立负责的核心思想，但适配了 15 人内部工具的规模

**文档产出**：design/11-模块化架构方案.md

### 2.3 MECE 原则 —— 结构检验工具

**来源**：麦肯锡 Barbara Minto《金字塔原理》（1973）

**核心定义**：Mutually Exclusive（相互独立）, Collectively Exhaustive（完全穷尽）

**借鉴方式**：从五个维度（功能模块、用户角色、数据模型、TDL 生命周期、交互场景）对系统做交叉验证，找出重叠和遗漏

**实际产出**：10 个初始问题 → 二次审视后保留 3 个真问题（委派交互、已拒绝状态、cancel_reason），去除 6 个框架逼出来的理论问题

**教训**：分析框架本身也可能产出虚假问题。框架是工具，不是目的。需要二次审视，区分"框架逼出来的"和"真实存在的"。

**文档产出**：design/12-MECE审视与优化.md

### 2.4 企业 AI 转型三步框架 —— 质量评估标尺

**来源**：AI 转型方法论（已保存为系统记忆）

**三步走**：① 明确岗位职责 + 产出标准 → ② 梳理落地流程 + 显性化判断标准 → ③ AI 提效实施

**借鉴方式**：用三步框架对照 TDL 当前完成度做差距分析

**核心发现**：
- 第一步完成度极高（★★★★★）
- 第二步骨架完整但核心动作（显性化判断标准）只做了开头（★★）
- 第三步已进入 MVP 联调期，但从"能跑"走向"判断更像李珍"还有距离

**关键洞察**：**AI 是放大器**。如果专家的判断逻辑没有被显性化，AI 就只能依赖通用推理。通用 AI + 数据 vs 专家经验产品化后的 AI——后者才是真正的壁垒。

**文档产出**：design/08-AI转型框架对照与差距分析.md

### 2.5 集装箱三层论 —— 战略视角启发

**来源**：一篇关于企业 AI 转型的文章，用集装箱革命比喻企业转型

**三层论**：第一层任务提效 → 第二层组织重构 → 第三层生态位重塑

**借鉴方式**：帮助少巍理解 TDL 系统在整个公司数字化中的位置——不只是"任务管理工具"，而是管理层操作系统的基建

**核心启发**：不要用旧框架里的人和流程去硬塞 AI。要开新地、做新事。TDL 系统本质上是在旧组织旁边开的新地。

### 2.6 三层知识管理架构 —— 组织知识沉淀

**来源**：社区实践参考

**三层结构**：弱文件夹层 → 规则层 → Wiki 层

**映射到 TDL 系统**：

| 知识层 | 对应物 |
|--------|--------|
| 弱文件夹层 | `励步5月月度会/`、`斯坦月度会/`、`各岗位薪资绩效/` 等原始材料 |
| 规则层 | `design/`、`config/` |
| Wiki 层 | `assets/`（管理者档案、组织关系网络、风险地图等） |

**决策**：MVP 不做正式知识库功能，先维持轻量三层结构。第 2 阶段再补组织记忆层的系统化。

**文档产出**：design/07-暂存需求决策记录.md §四

### 2.7 双 MVP 验证策略 —— 风险对冲方法

**来源**：对照 AI 转型框架差距分析后的自主设计

**核心思路**：月会决议闭环（难度高，验证 AI 的"理解+拆解+结构化"能力）+ 薪资月度流程（难度低，验证系统"提醒+推动+回收"能力），两个场景并行推进，互为对照

**逻辑**：如果薪资跑得顺但月会跑不顺 → 问题定位在"输入→AI拆解"环节；如果都跑不顺 → 问题在基础能力

**文档产出**：design/08-AI转型框架对照与差距分析.md §三

## 三、平台与技术选型决策

### 3.1 双层入口架构

**决策**：钉钉承载主交互（文本+卡片），飞书承载数据分析（多维表格）

**理由**：
- 钉钉是管理层日常办公主平台，全员使用
- 飞书多维表格已是薪资系统的载体，数据仪表盘自然延续

**后续调整**：语音交互从 MVP 推迟到 V1.1（Realtime-2），MVP 用钉钉 Stream 模式机器人做纯文本+卡片交互

### 3.2 AI 模型策略

**初始设计**：OpenAI 主 + DeepSeek 备（failover）。关键链路不自动降级

**中间调整**：经 MECE 审视和成本考量后，提出模型分层调用策略——日常高频操作（字段提取、标签分类、提醒文案）走 DeepSeek，关键链路（会议纪要拆解、能力分析、战略分析）走 OpenAI

**状态**：分层策略已确认方向，具体实现待下个 PR

### 3.3 日历集成方案

**初始设计**：应用级日历接口

**问题**：应用级接口对个人日历写入支持不完善

**调整**：改为个人 OAuth 授权模式——每位管理者首次授权一次后，系统以其个人身份写入钉钉日历

**遇到的实际问题**：`DINGTALK_OAUTH_CLIENT_ID` 配置为错误应用导致授权失败 → 修复为直接使用 `DINGTALK_APP_KEY`

**文档产出**：design/09-Cowork接手指南-2026-05-17.md §二

### 3.4 架构：从线性到模块化

**初始模式**：Codex 按线性批次开发（批次 1→2→3→...）

**困惑**：少巍难以把控 AI 开发的实际完成度、无法验证真实使用体验、无法判断是否真正做到了模块化拆分

**调整**：提出模块化积木式架构（参考《天道》农户模式）→ 经分析后确定"模块化单体 + 接口契约层"方案

**文档产出**：design/11-模块化架构方案.md

## 四、开发流程与方法论

### 4.1 Codex + Claude 协作模式

**角色分工**：
- **Codex**：主开发、测试、部署、开 PR、处理 review、合并
- **Claude**：只审 PR，挑漏洞，提出风险和测试缺口
- **少巍**：最终裁决范围、业务判断、关键外部授权

**核心原则**：一个 owner 写主线，一个 reviewer 挑问题。避免两个 AI 同时改文件。

**实际经历的问题**：
- Codex 把 review 消息拆成多条发给 Claude → SOP 明确要求一条完整消息
- Codex 额度耗尽 → Cowork（Claude）接手 4 天，处理了 PR #42-#47
- GitHub 私有仓库访问限制 → Claude 通过本地分支审 PR

**文档产出**：design/10-Codex-Claude-PR协作SOP.md、design/09-Cowork接手指南-2026-05-17.md

### 4.2 部署流水线

```
本地改代码 → 服务器验证 → git commit + push →
GitHub 自动创建 PR → Claude 审核 → API 合并 →
rsync 部署到生产 → systemctl restart → 健康检查 → 钉钉推送通知
```

部署目标：阿里云 ECS 182.92.9.69，两个 systemd 服务（tdl-backend + tdl-stream-bot），Nginx 反向代理

### 4.3 测试策略

- **单元测试**：144 个，覆盖核心 service 和 intake 逻辑
- **场景测试**：7 个用户场景（从"个人任务自动创建"到"协作不误指派"）
- **会议录入评测**：DeepSeek 参考版离线评测，29 条人工基准对照，召回率约 31%（未达标，不进入生产）

**文档产出**：design/10-TDL试点测试方案-2026-05-17.md、design/12-会议录入小样本试点方案-2026-05-17.md、励步5月月度会/01-会议录入DeepSeek参考评测-2026-05-17.md

## 五、中间调整与困惑解决

### 5.1 产品化定位的校准

**初始思考**：系统未来可否作为可出售的产品？

**中间困惑**：换一家公司能否直接部署？

**最终校准**：不做跨行业通用 SaaS。定位为"品牌内复刻"——励步英语和斯坦星球的自有品牌，新校区/新城市启动时改配置即可部署。不需要多租户抽象。

### 5.2 模块化程度的校准

**初始思考**：参考《天道》农户模式，每个模块独立负责、独立交付

**中间困惑**：会不会过于理想化？现有技术栈下是否可行？

**最终校准**：不拆微服务（单机 ECS 15 人的规模不需要）。保留"模块独立负责"的核心思想，但实现方式是"模块化单体 + Python Protocol 接口契约"——改动量约 120 行，不推倒重来。

### 5.3 MECE 审视的自我校正

**初始输出**：用 MECE 找到 10 个问题

**二次审视**：少巍追问"到底是不是真问题？还是顺着 MECE 框架硬凑的？"

**最终判断**：去除了 6 个理论问题（架构分类不纯、缺少搜索、运维监控缺失等），保留 3 个有工程价值的真问题（委派交互、已拒绝状态、cancel_reason）。教训：分析框架是工具不是目的，需要二次审视区分真伪。

### 5.4 会议录入的务实判断

**初始计划**：月会纪要→决议→TDL 是 MVP 核心验证目标

**实际测试**：DeepSeek 参考版召回率约 31%，OpenAI 连通性阻塞生产链路

**中间决策**：会议录入停在离线评测阶段，不进入钉钉真实交互。日常 TDL 助手继续小范围试用。先解决 OpenAI 连通性和抽取策略。

### 5.5 交互体验的渐进优化

**实际发现的问题**（来自 Cowork 接手期间的实测）：
- 草稿卡片"忽略"按钮无反应 → 修复回调注册
- 卡片按钮没有视觉反馈 → 增加工作通知确认
- 日历事件描述只有一个 UUID → 改为富文本
- follow-up 守卫过于粗暴 → 待优化
- 语音输入同音字问题 → 待加模糊匹配
- AI 不擅长处理"元信息"（纠正/澄清类消息）→ 待增强 prompt

### 5.6 从“抽任务”到“先理解业务，再抽任务”

**触发问题**：在讨论 5 月月会材料试跑时，少巍追问“系统面对 7 份材料时，到底是只提任务，还是先把业务理解吃透？”

**关键判断**：如果只机械抽取任务，系统最多是“会议纪要转待办工具”；但企业真实管理需要先看懂：

1. 本月经营主题
2. 关键矛盾
3. 目标、风险、任务之间的关系
4. 各管理者之间的协同与前后依赖

**调整后的路线**：

`逐文件业务理解 → 形成经营主题图 → 抽取任务 → 跨文件合并去重 → 依赖与节奏校验 → 生成 TDL`

**意义**：TDL 不再只追求“把任务建起来”，而是开始承担“把管理动作放回整盘棋中理解”的责任。

**文档产出**：

- `励步5月月度会/02-会议录入非生产真实链路试跑方案-2026-05-18.md`

### 5.7 从“任务助手”到“企业经营操作系统雏形”

**触发问题**：少巍指出，未来系统会联动薪资、考勤、销售、培训、招聘等系统，并进一步支撑：

1. 企业战略蓝图
2. 企业节奏把控
3. 任务优化
4. 经营策略优化

**关键判断**：这说明项目已经越过“单纯建任务条目”的阶段。后续真正要建设的，不只是任务表，而是：

1. 素材层
2. 企业知识中台层
3. 发布/表达层
4. 调用/插件层

其中知识中台至少要沉淀：

- `Entity`
- `Fact`
- `Relation`
- `Event`
- `Goal`
- `Task`
- `Decision`
- `Risk`
- `Metric`

**已有知识库的启发**：

- 励步知识底座已经形成“素材层 → 中台层 → 发布层 → 调用层”的清晰分层，并把结构、判断、过程数据分开。
- 斯坦星球知识库已经把“图谱化可连接”“程序可消费”“上游底座与下游成品分离”固化成原则。

**新的项目定位**：

> 以任务为最小执行单元、以知识层为中枢、可被多个经营插件调用的企业经营操作系统雏形。

**文档产出**：

- `design/15-企业知识层与插件化路线设计-2026-05-18.md`

### 5.8 会议内容判定从“能提取”转向“先守边界”

**触发问题**：在重看 5 月月会材料时，少巍指出：如果把“会上说过”“个人述职中想过”“只是有方向感”的内容，提前加工成“已经决定执行”，会让管理者在收到 TDL 提醒时产生强烈错位感。

**关键判断**：

> 对 TDL 来说，错把“说过”当“决定做”，不是普通误差，而是直接伤害系统信用的一级错误。

一旦管理者觉得：

- “我们确实说过这件事”
- 但“并没有决定现在就做”

系统就会失去最关键的信任基础。

**最终决议**：

除客观事实外，只有同时满足以下三项，才允许进入“已明确事项”：

1. `What`：做什么明确
2. `Who`：谁负责明确
3. `When`：开始时间或完成时间明确

否则必须落在：

- `待处理议题`
- `火花/设想`
- `观察线索`

而不能直接流转成 TDL。

**意义**：

- 系统从“尽量多提任务”转向“先把边界守住”
- 会议录入从信息抽取问题，升级为组织认知分层问题
- 后续插件能力必须建立在准确标签之上，不能建立在被 AI 过度加工的伪事实之上

**文档产出**：

- `design/16-会议内容判定口径-2026-05-18.md`

### 5.9 三方共建流程的再次收紧

**触发问题**：少巍将 `17-项目原始诉求与终局基线-V1` 和 `18-项目落地实现路径-V1` 交给 Claude 审。Claude 认可 17 号作为冻结基线，但指出 18 号在多 agent、90 天节奏、人机交接、知识层建表四处存在落地风险。

**采纳的校正**：

1. 多 agent 不拆成 6 个运行体，改为“一个主流程 agent + 一个专项审查 agent”。
2. 0-30 天路线不再硬承诺跑完 5 月材料非生产评测，改为力争项。
3. 增加人机交接条件，AI 不能在未达标前自动把火花、议题、线索升级成执行提醒。
4. 当前阶段不允许新建知识层正式表，知识层只做 schema 草案、离线评测和样例。
5. 三方协作按“Codex 评估实现成本、Claude 审风险、少巍拍板”处理分歧，不让两个 AI 互相辩论扩大范围。

**意义**：

- 把愿景进一步压回可执行路径。
- 防止工程惯性提前实现知识层 schema。
- 防止多 agent 变成过度工程。
- 保持“主开发 + 审核 + 用户拍板”的共同体闭环。

**文档更新**：

- `design/18-项目落地实现路径-V1-2026-05-18.md`
- `design/10-Codex-Claude-PR协作SOP.md`

### 5.10 开发节奏切换为“先重梳，再开发”

**触发问题**：少巍指出，当前不应该继续惯性开发，而要先停下来，把 `18-项目落地实现路径-V1` 中后续要推进的系统板块重新梳理一遍，再校准整体系统开发方向和落地性。

**新确认的推进方式**：

1. 暂停新增功能开发。
2. 先重梳日常 TDL、会议录入、非任务对象、企业知识层、跨系统事实源、插件、多 agent、协作流程等板块。
3. 每一次重要更新都必须合并 PR 到 Git 仓库。
4. 文档更新也要纳入 Codex 整理、Claude review、用户拍板、PR 合并的闭环。
5. 17 号冻结基线不回写，后续变化通过 V2/V3 或其他路线文档记录。

**意义**：

- 防止项目在愿景变大后继续以单点补丁方式推进。
- 防止“会议录入”“知识层”“插件”“多 agent”互相抢优先级。
- 把开发节奏从“继续加功能”切换为“先把方向压实，再恢复开发”。

## 六、已知局限与待解决问题

### 6.1 当前阶段判断（2026-05-17）

系统处于"可控试点阶段"：
- 可以进入少量真实任务试用
- 不适合直接大范围替代人工 TDL 管理
- 试点重点：验证"录入 → 补充/纠错 → 确认/忽略 → 提醒/日历 → 状态回收"的直觉性

### 6.2 MVP 明确不做的事

| 事项 | 原因 |
|------|------|
| 钉钉 H5 实时语音（Realtime-2） | V1.1 |
| Web 可视化仪表盘 | 用飞书多维表格代替 |
| OKR 自动对齐检查 | 没有真实维护的 OKR 数据源 |
| 审批流/文档深度嵌入 | 平台工程，非 MVP 核心 |
| 团队公开排名 | 推广后才考虑 |
| 复杂日历联动 | 仅做单向写入 |
| 长期行为记忆与画像 | 数据量不够时是噪音 |

### 6.3 已知 AI 判断边界

- "给李珍提交工作总结" → AI 可能判负责人为李珍，实际应是发送者
- "和李珍一起做复盘" → 协作场景 vs 委派场景的区分
- 语音转录错字（李珍→李祯）→ 需要模糊匹配纠正
- 纠正/澄清类消息 → AI 容易当成新任务而非对草稿的修改

### 6.4 下个 PR 待做

1. 任务委派交互（解析 @ 列表 + 委派卡片 + 被委派人通知）
2. TDL `cancel_reason` 字段
3. 状态机增加「已拒绝」→「草稿」路径
4. 对话式修正路径（扩展 follow-up 逻辑支持修正意图）
5. AI 模型分层调用（日常→DeepSeek，关键链路→OpenAI）
