# 32 · 工作台权限身份与待确认操作路线 — 2026-05-24

## 一、本文定位

本文承接 `30-管理工作台与钉钉通道化路线校准` 和 `31-管理工作台V0验收清单`，用于收口工作台从只读查看进入可操作产品前必须回答的三个问题：

1. 待确认 / 待判断任务以后怎么处理。
2. 管理者能看哪些内容，权限怎么判定。
3. 工作台未来接钉钉还是飞书，身份主键应该怎么设计。

本文不修改 `17-项目原始诉求与终局基线-V1`。本文也不开放写入能力，只定义后续进入写入前的顺序和边界。

## 二、当前现场结论

2026-05-24 本机工作台试用后，Frank 和 Helen 的反馈是：

1. 工作台整体清晰，比钉钉任务卡更全面、更直观。
2. Frank 视角下大量待确认 / 待判断内容的布局可以接受。
3. 当前待确认内容多为历史测试数据，不代表最真实的业务任务。
4. 页面目前只能看，不能确认、忽略或删除。
5. 后续必须补权限管理和登录身份设计，否则不能把工作台开放给更多管理者。

因此，工作台方向继续推进，但下一步不能直接做写入按钮。

## 三、待确认项的处理顺序

### 3.1 不直接开放三类按钮

当前不直接在工作台上开放：

1. 确认。
2. 忽略。
3. 删除。

原因：

1. 这些动作都是写入行为，会改变任务状态或数据存在性。
2. 当前工作台没有身份认证，无法确认操作者是谁。
3. 当前工作台没有权限判断，无法确认操作者是否有权处理该任务。
4. 当前工作台没有操作审计，无法追踪谁处理了什么。
5. 当前待确认项中混有历史测试数据，不能用它们直接验证真实业务写入体验。

### 3.2 先做待确认清理口径

进入写入前，先把待确认项分成四类：

| 分类 | 含义 | 后续动作 |
|---|---|---|
| 可确认 | 内容真实、负责人和截止时间可补齐 | 后续允许进入确认流程 |
| 可忽略 | 内容无效或不应成为任务 | 后续允许进入忽略 / 拒绝流程 |
| 可删除 | 明确是测试数据或脏数据 | 由管理员清理，不作为普通管理者能力 |
| 待补信息 | 需要补负责人、时间、完成标准 | 后续进入补字段流程 |

V0.1 可以先做只读标记或人工记录，不急于把这些动作做成页面按钮。

### 3.3 写入能力的最小顺序

若后续开放操作，顺序应为：

1. 只读详情页：先让管理者看清单条任务的来源、缺失字段和推荐动作。
2. 补字段草稿：只允许补负责人、截止时间、完成标准，不直接确认。
3. 确认任务：把完整草稿转为正式任务。
4. 忽略 / 拒绝：保留原因和操作者。
5. 删除：仅限管理员处理测试数据或脏数据，普通管理者不开放。

每一步都必须有测试、权限判断和审计记录。

## 四、权限管理原则

### 4.1 `owner_id` 不是权限

当前 URL 中的 `owner_id` 只能作为视角筛选，不能作为身份认证或权限控制。

不允许：

1. 通过修改 URL 参数查看他人视角。
2. 把 `owner_id=xxx` 当作“当前登录人是 xxx”。
3. 用前端隐藏按钮替代服务端权限判断。

### 4.2 权限必须服务端判断

后续正式开放工作台时，所有 API 必须在服务端判断：

1. 当前登录人是谁。
2. 当前登录人拥有哪些角色。
3. 当前登录人能看哪些组织、业务线、部门、任务。
4. 当前登录人能执行哪些动作。

前端只能负责展示，不承担权限判断。

### 4.3 初始权限范围

V0.1 建议采用最小权限模型：

| 角色 | 可见范围 | 可操作范围 |
|---|---|---|
| CEO / 总负责人 | 全部管理任务 | 后续可操作全部，但需审计 |
| 业务负责人 | 自己业务线和下属团队任务 | 后续可处理自己范围内任务 |
| 任务负责人 | 自己负责或参与的任务 | 后续可处理自己任务 |
| 技术管理员 | 调试和维护视角 | 不默认拥有业务处理权 |

Frank 在当前试验中同时是技术开发者和业务管理者，后续正式权限设计必须把这两个身份分开。

### 4.4 当前花名册的作用

`config/management_roster.yaml` 当前可以继续作为权限原型的数据来源，因为它已经包含：

1. 管理者姓名。
2. 英文名。
3. 钉钉 user_id。
4. 角色。
5. 管辖范围。
6. 汇报关系。

但它还不是正式权限系统。后续若工作台进入正式使用，应迁移为数据库中的组织和权限配置，或至少建立可审计的配置发布流程。

## 五、平台与身份绑定

### 5.1 短期以钉钉为登录入口

当前项目已有：

1. 钉钉机器人。
2. 钉钉 user_id。
3. 钉钉工作通知。
4. 钉钉日历授权。
5. 生产任务中的 `owner_id` 已使用钉钉 user_id。

因此，短期最稳妥的工作台登录方式是钉钉 OAuth / 钉钉身份。

这不代表长期只支持钉钉，而是因为当前数据和通知链路已经围绕钉钉建立。

钉钉 OAuth 只用于确认“当前访问者是谁”，不代表把工作台交互能力退回钉钉任务卡。

### 5.2 不把钉钉 ID 作为长期人员主键

长期不应把钉钉 ID 或飞书 ID 当作系统人员主键。

建议建立内部管理者身份：

```text
internal_user_id
name
role
scope
dingtalk_user_id
feishu_user_id
status
```

业务数据归属内部身份，外部平台 ID 只作为登录和通知映射。

这样后续即使接入飞书，也不需要重写所有权限逻辑。

### 5.3 飞书的定位

飞书可以作为候选技术支撑，但不作为 V0.1 前置依赖。

飞书适合评估的方向：

1. 多维表格承接低代码数据视图。
2. 部门协作看板。
3. 数据填报或审批。
4. 薪资、绩效等已有飞书流程的衔接。

但飞书不应在当前阶段倒推主系统身份设计。

## 六、下一阶段建议

下一阶段不要直接开发完整权限系统，也不要直接开发确认 / 删除按钮。

建议顺序：

1. 做一版只读任务详情页。
2. 在详情页展示缺失字段、来源、负责人、推荐动作。
3. 补一份“待确认项清理表”，人工标注 21 条历史数据属于可确认、可忽略、可删除还是待补信息。
4. 设计最小登录方案：钉钉 OAuth 登录后得到当前用户身份。
5. 设计最小权限判断：只能查看自己、下属或全局范围内的任务。
6. 等登录和权限边界成立后，再开放第一个写入动作。

第一个写入动作建议不是删除，而是“忽略 / 拒绝并记录原因”。

原因是：忽略 / 拒绝能清理待确认池，但风险低于删除；确认任务会进入正式执行链路，风险更高；删除会破坏追踪，不适合作为普通用户能力。

若后续确实需要清理测试数据或脏数据，也应优先采用软删除、取消状态或保留审计痕迹的方式，不做普通物理删除。
