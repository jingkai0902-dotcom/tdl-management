# 30 · 管理工作台与钉钉通道化路线校准 — 2026-05-24

## 一、本文定位

本文是对 `29-外部工作台与半路改造讨论整理` 的正式路线收口。

`29` 记录讨论过程、外部材料、Claude 反馈和技术诉求；本文只固化当前已经拍板的路线结论、边界和下一步执行口径。

本文不修改 `17-项目原始诉求与终局基线-V1`。`17` 仍是冻结版终局基线。本文用于校准 `18 / 19 / 23` 后续阶段执行口径。

## 二、已确认决策

### 2.1 钉钉任务卡不再作为主交互面

已确认：

> 钉钉任务卡不再作为主交互面继续重投入。

含义：

1. 不再围绕复杂钉钉任务卡体验继续追加大量功能。
2. 不再把钉钉卡片当成完整管理界面。
3. 不再以“钉钉任务卡是否可推广”作为下一阶段主验收目标。
4. 现有钉钉任务卡链路暂不物理删除，作为过渡能力保留。

### 2.2 钉钉保留为通知通道

已确认：

> 钉钉保留为通知通道。

含义：

1. 钉钉继续承担主动触达价值。
2. 钉钉可用于逾期、临期、待确认、协作提醒。
3. 钉钉消息应尽量简洁，不承载复杂管理界面。
4. 后续可探索从钉钉通知跳转到工作台处理。

新的分工是：

| 层面 | 定位 |
|---|---|
| 管理工作台 | 主交互面候选，承载全局查看、任务整理、资料入口、报告草稿 |
| 钉钉 | 通知触达通道，承载提醒、催办、待确认提示 |
| TDL 引擎 | 后端任务能力，承载入库、状态、提醒、日历、审计 |

## 三、工作台 V0 范围

### 3.1 V0 强范围

工作台 V0 的强范围正式定为：

1. 今日。
2. 本周。
3. 逾期 / 临期。
4. 进行中。
5. 待确认 / 待判断。

V0 的目标是验证：

> 小团体每天打开工作台后，是否能比钉钉任务卡更清楚地看到当前要处理什么、什么已经卡住、什么需要确认。

### 3.2 V0 不做范围

V0 暂不做：

1. 会议待复核。
2. 议题池。
3. 火花池。
4. 观察线索。
5. 快捷 agent 指令。
6. 自动报告生成。
7. 任务写入和状态修改。
8. 飞书多维表格深度接入。
9. Obsidian 正式知识库建设。
10. CodeGraph 接入。

这些内容可以作为后续候选，但不能进入 V0 强范围。

### 3.3 V0 技术边界

V0 必须遵守：

1. 只读优先。
2. 旁路优先。
3. 不写库。
4. 不发钉钉。
5. 不改任务状态。
6. 不授予 agent 执行权。
7. 每个数字和列表都要能说明数据来源。

## 六、半路改造原则

半路改造原则正式纳入后续开发约束：

> 旁路优先、只读优先、叶子模块优先、有测试再写入。

具体要求：

1. 不按代码行数判断模块改造风险。
2. 先做依赖度评估，优先选择低入度、低出度、职责单一的叶子模块。
3. 优先改读取型、展示型、聚合型模块。
4. 不先改钉钉 Stream、提醒调度、日历写入、AI 解析、TDL 状态流转等核心链路。
5. 没有测试覆盖的写入能力不开放。
6. 开放写入前必须补状态流转、通知、日历、人名匹配、AI 解析降级等测试。
7. 任何“顺手加按钮 / 顺手加写入 / 顺手让 agent 执行”的需求，都必须先回到本原则审查。
