# 12 · 多维度审视与优化

> 本文从 MECE 结构完备性、商业价值、客户体验、技术实现四个维度审视 TDL 系统，找出真实问题并给出优化建议。
>
> 经过二次审视，去除了被分析框架逼出来的理论问题，保留经得起推敲的真问题。

---

## 一、审视经过说明

首次用 MECE 五步法对功能模块、用户角色、数据模型、TDL 生命周期、交互场景五个维度做交叉验证，产生了 10 个问题。与少巍讨论后，对每个问题做了真实性再审：

**去除的 6 个（框架逼出来的理论问题）：**

| 问题 | 去除理由 |
|------|---------|
| 五模块与六插件分类维度混用 | 架构审美问题。Codex 不会因为分类不纯写错代码，15 人内部工具不需要教科书级架构纯度 |
| 李珍双层角色未区分视图 | MVP 15 人规模下，李珍同时收到执行提醒和战略简报不会造成认知混乱，手动判断足够 |
| 缺少任务搜索 | MVP 阶段 15 人每周几十条 TDL，不需要搜索引擎。数据量上来后再说 |
| 系统运维监控缺失 | 单机部署，少巍自己看日志和 systemctl status 就够了。需要时再补 |
| 任务合并/去重缺失 | 低频场景。两个人给同一个人创建相同 TDL 的概率极低，人工处理即可 |
| 底层执行者不在角色模型里 | MVP 不涉及全员推广，执行层用户的建模是推广期的事 |

**保留的 3 个（有实际工程价值的真问题）：**

| 问题 | 为什么是真问题 |
|------|-------------|
| 缺少任务委派交互 | 管理者日常操作里高频出现——"把活派给你"没有系统化入口。当前只能靠自己给自己建 TDL |
| 缺少「已拒绝」状态 | AI 推断的 owner 可能不准，owner 需要说"这不是我的事"的路径。状态机里没有 |
| 缺少 `cancel_reason` 字段 | 取消的 TDL 无法分析原因，P1 管理者能力模型缺少一个关键数据维度 |

下面从四个维度展开审视——商业价值、客户体验、技术实现、MECE 结构。每个维度只记录真实问题。

## 二、商业价值维度

### 2.1 定位校准

产品化方向不是"跨行业通用 SaaS"，而是**品牌内复刻**。少巍经营的自有品牌（励步英语、斯坦星球），开新校区或新城市时，系统能直接部署。这大大降低了产品化门槛——不需要多租户抽象，不需要行业无关的通用配置模型。

### 2.2 真正的问题：产品化资产没有沉淀

当前系统的行业 know-how 散落在三个地方，没有形成可复用的产品资产：

| 资产 | 当前状态 | 应该是 |
|------|---------|--------|
| 标签词典 | 02 号文档硬编码励步/斯坦的业务域 | 品牌模板化的标签词典，新校区启动时选模板即可 |
| GTD 流程 AI 行为 | 散落在 `ai_service.py` 的 prompt 和 `tdl_rules.yaml` 的规则里 | 独立的行为规则包，可替换、可版本管理 |
| 管理层配置 | 硬编码在 YAML 里，包含 12 个人的钉钉 ID | 标准的导入模板 + 角色-权限映射表 |
| 提醒语气设计 | 散落在 04 号文档和代码注释里 | 独立的语调配置文件（中文/英文/行业术语变体） |

真正能构成商业壁垒的不是代码，是这三样：行业标签词典的深度、GTD 流程的 AI 行为定义、提醒语气的设计哲学。但目前这三样都是隐式知识，没有被显式抽取为可复用的独立资产。

### 2.3 建议

**MVP 阶段不急着产品化，但做一件事**：把标签词典、AI 行为规则、管理层配置模板从代码里抽到独立的配置层（`config/` 下已有部分，补全即可）。保证换一个励步新校区时，改配置不改代码就能部署。

## 三、客户体验维度

### 3.1 已澄清的担忧

**回复延迟**：少巍认为 3-5 秒的 AI 响应延迟可以接受。真人沟通里对方在忙、隔很久才回复是常态。这个担忧消除。

**学习成本**：少巍的思路是通过草稿卡片提示缺失字段——截止日期、交办给谁、需要准备的材料、简单的效果描述。用户在卡片上看到"还缺什么"，自然就知道该补什么，不需要学一套"跟机器人说话的格式"。这个交互方向正确，且当前草稿卡片已经部分实现了（`missing_fields` + `recommended_fields`），补全即可。

### 3.2 真正的体验问题

**问题一：AI 识别错误后修正路径太长**

当前修正路径：AI 返回草稿卡片 → 用户发现 owner 错了 → 点「改负责人」按钮 → 在卡片上改 → 确认。如果 AI 搞错了两个字段（比如 owner 和 due_at 都错了），需要点两次、改两次。

更短的路径：用户在对话里追加一句"负责人改成张三，时间改到下周五"，系统识别为对最近一条草稿的修正，直接更新卡片。这是对话式修正——和真人群聊里说"不对不对，改成张三"的体验一致。

建议实现方式：`intake_service.py` 里 `find_latest_incomplete_draft` 的逻辑已经存在（找 15 分钟内的未完成草稿），扩展为：如果找到最近草稿且新消息包含修正意图关键词（"改成""改到""不是""应该是"），则走 follow-up 更新路径而非创建新 TDL。当前代码已有 follow-up 逻辑的雏形（`extract_tdl_follow_up`），扩展支持更多修正场景即可。

**问题二：草稿卡片提示不够具体**

当前草稿卡片缺失 `owner_id` 时标「待补充」，但没有给出补充什么内容的引导。优化为：

```
┌────────────────────────────────────────┐
│ 📌 TDL 草稿                             │
│                                        │
│ 斯坦星球暑期班课程方案审核                │
│ ├─ 负责人：[❓ 需要补充]                 │
│ ├─ 截止：[❓ 需要补充]                   │
│ ├─ 优先级：P1-重要不紧急                 │
│ └─ 完成标准：[💡 建议补充]               │
│                                        │
│ 💡 还差这些就可以创建了：                 │
│    1. 谁来负责？                        │
│    2. 什么时候完成？                     │
│                                        │
│ [👤 指定负责人] [📅 指定时间]            │
└────────────────────────────────────────┘
```

### 3.3 建议

1. 下个 PR 扩展 `extract_tdl_follow_up` 支持修正场景，实现对话式追加修正
2. 草稿卡片增加引导提示文案，区分「必须补充」和「建议补充」

## 四、技术实现维度

### 4.1 架构选型：无问题

FastAPI + PostgreSQL + 钉钉 Stream + 阿里云 ECS 单机部署——当前规模和可预见的增长（15→50 人）下没有任何架构层面的问题。不需要微服务、不需要消息队列、不需要容器化。

### 4.2 AI 调用成本：需要模型分层策略

少巍提出了模型分层调用的思路：高价模型（OpenAI GPT-5.5）用在关键链路，常规操作用国产模型（DeepSeek V4 Pro）。这与 05 号文档的设计一致但更激进——当前设计是 OpenAI 主 + DeepSeek 备（failover），少巍的方案是 DeepSeek 主（常规操作）+ OpenAI 专（高价值场景）。

建议的分层：

| 场景 | 模型 | 理由 |
|------|------|------|
| 会议纪要拆解 | OpenAI | MVP 核心，准确率要求最高，一次月会几十条 TDL 错不起 |
| 管理者能力分析 | OpenAI | 第 2 阶段，分析质量直接影响帮扶建议的有效性 |
| 战略分析报告 | OpenAI | 第 3 阶段，面向投资人的产出需要高质量 |
| 日常字段提取 | DeepSeek | 高频调用，容错空间大（错了用户可以在卡片上改） |
| 标签分类 | DeepSeek | 有标签词典硬约束，模型要求不高 |
| 提醒文案生成 | DeepSeek | 简单文案，国产模型完全胜任 |
| 周报数据统计 | 不需要模型 | 纯 SQL 统计，不调 AI |
| 日历同步 | 不需要模型 | 纯 API 调用 |

这个分层策略直接省钱——日常高频调用走 DeepSeek，月度/战略级场景走 OpenAI。需要改 `ai_client.py`，让调用方可以指定模型而非总是用默认模型。

### 4.3 钉钉 Stream 稳定性：需要压测数据

Stream 长连接的断线重连、消息丢失、心跳策略——你之前在音频分析项目里跑过，应该有体感。但 15 个人同时高频使用（每人每天 5-10 条消息 + 系统主动推送提醒 + 卡片回调）的并发场景还没有数据。

建议在批次 7（部署）的 smoke test 里加一项：模拟 15 个用户在 30 分钟内各自发送 5 条消息，检查消息是否有丢失、卡片回调是否正常。

### 4.4 技术壁垒：不在代码，在数据和规则

从纯技术角度，FastAPI + 钉钉 + AI 调用的组合没有复制门槛。真正的壁垒是：
- 标签词典的行业深度（培训行业 11 个职能域 × 各域关键动作 × 业务线产品线标签体系）
- GTD 五步流程的 AI 行为规则（什么时候自动创建、什么时候草稿确认、什么时候追问什么）
- 提醒语气设计（不说"逾期"说"需要关注"——这个设计哲学是管理理念的编码）

这些目前散落在代码和文档里。如果要形成壁垒，需要抽取为独立的规则包，可版本管理、可复用。

## 五、MECE 结构维度：保留的真问题

### 5.1 问题一：缺少任务委派交互

**维度**：交互场景 × 功能模块

**表现**：当管理者 A 在钉钉里对机器人说"@邢杨 下周五前把续费数据统计出来"，当前系统会把这条消息当成 A 自己的 TDL 来处理（owner 推断逻辑里，如果没检测到委派意图，默认 owner = sender）。但实际上这是一次委派。

**影响**：管理者最自然的交互方式——在群里 @ 人安排工作——和系统的 TDL 创建入口不重合。如果每次委派都需要管理者"先口头交代，再到机器人这里录一遍"，系统就成了额外负担而非效率工具。

**解决**：扩展 `intake_service.py` 的 `_infer_assigned_owner_id` 逻辑，在钉钉 Stream 消息里解析被 @ 人的 user_id（Stream 模式可拿到 at 列表）。同时走委派交互路径：给委派人确认卡片 + 给被委派人通知卡片。具体交互设计见第六节。

### 5.2 问题二：缺少「已拒绝」状态

**维度**：TDL 生命周期

**表现**：当前状态机里，TDL 被 AI 创建后，owner 只能确认、完成、延期、暂缓——没有一个"这不是我的事"的出口。如果 AI 推断的 owner 错了，对方只能忽略这条 TDL，系统没有纠正机制。

**影响**：AI 推断 owner 的准确率约 80%，意味着每 5 条 TDL 可能就有 1 条 owner 不对。15 个人每周几十条 TDL，被错分的人会在钉钉里收到跟自己无关的提醒和追问——伤害对系统的信任。

**解决**：状态机增加「已拒绝」状态：

```
进行中 ──→ 已拒绝 ──→ 草稿（退回创建者，重新分配 owner）
```

卡片上增加「这不是我的事」按钮。点完后 TDL 回到草稿状态，通知创建者重新指定负责人。

### 5.3 问题三：缺少 cancel_reason 字段

**维度**：数据模型

**表现**：TDL 可以被取消，但没有记录取消原因。当 P1 管理者能力模型分析某管理者的行为模式时，缺少一个关键维度：他的 TDL 有 30% 被取消了——是因为重复录入？不再需要？还是委派错了？

**影响**：取消率高不一定代表执行差，可能代表"他的工作性质变化快，很多 TDL 过两天就不需要了"。但没有原因分类，分析模型只能看到"取消率高"这个事实，无法判断是好是坏。

**解决**：TDL 表增加 `cancel_reason` 字段，可选值：`user_cancelled`（我自己决定不做了）/ `duplicate`（重复了）/ `delegated`（转给别人了）/ `no_longer_needed`（业务变化不需要了）。取消卡片上增加原因选择。

## 六、优先级与行动计划

### 6.1 问题汇总

| # | 问题 | 维度 | 严重程度 | 改动成本 |
|---|------|------|---------|---------|
| A | 缺少任务委派交互 | 体验 | 🔴 高频场景缺失 | 中（改 intake 逻辑 + 新增卡片模板） |
| B | 缺少「已拒绝」状态 | 结构 | 🟡 AI 误判时无法纠正 | 低（加一个状态 + 一个按钮） |
| C | 缺少 cancel_reason | 结构 | 🟡 数据维度缺失 | 极低（加一个字段 + 卡片选项） |
| D | AI 修正路径太长 | 体验 | 🟡 降低使用意愿 | 低（扩展已有 follow-up 逻辑） |
| E | 草稿卡片引导不够 | 体验 | 🟢 优化项 | 极低（改卡片文案） |
| F | AI 调用成本未分层 | 技术 | 🟡 月度费用不可控 | 低（改 ai_client 模型路由） |
| G | Stream 稳定性未压测 | 技术 | 🟡 有不确定性 | 中（需要 15 人并发模拟） |
| H | 产品化资产未沉淀 | 商业 | 🟢 MVP 不用急 | 低（整理配置即可） |

### 6.2 行动计划

**下个 PR 就做（优先级 A/B/C/D/F）**：

1. 扩展 `intake_service.py`：解析钉钉 @ 列表 → 委派意图识别 → 委派交互卡片
2. TDL 模型增加 `cancel_reason` 字段 + Alembic 迁移
3. 状态机增加「已拒绝」→「草稿」路径，卡片增加「这不是我的事」按钮
4. 扩展 `extract_tdl_follow_up` 支持修正意图（"改成""改到""不是""应该是"）
5. `ai_client.py` 增加 `model` 参数，调用方可指定模型；配置层增加模型分层规则

**批次 7 部署时做（G）**：
- Smoke test 增加 15 人并发消息测试

**第 2 阶段做（E/H）**：
- 草稿卡片引导文案优化
- 标签词典/AI 行为规则/管理配置从代码抽到独立配置层
