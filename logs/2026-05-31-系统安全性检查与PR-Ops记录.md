## 三、主要风险发现

### S1 - 高风险：核心 HTTP API 缺少统一认证授权边界

事实：

- `app/main.py` 默认注册 `/tdls`、`/dingtalk`、`/meetings`、`/reminders`、`/reports` 等路由。
- `app/api/tdl_crud.py` 的 `POST /tdls`、`GET /tdls` 没有认证依赖。
- `app/api/dingtalk_webhook.py` 的创建、确认、完成、暂缓、拒绝、批量确认等动作没有 HTTP 层认证。
- `app/api/meetings.py` 的会议 ingest / parse / results 没有认证依赖。
- `app/api/reminders.py` 的 `POST /reminders/run` 可以触发提醒周期。
- `app/api/reports.py` 的 `GET /reports/weekly` 可以生成周报视图。

判断：

如果生产 Nginx 将 `/tdl/` 下所有路径暴露到公网，外部请求理论上可以绕过钉钉 Stream 入口直接访问这些 API。当前代码更像“内部 API + Stream bot 同机调用”的形态，但部署片段没有把这种边界表达出来。

建议：

1. 第一优先级不是给每个端点临时补判断，而是先定清楚外部入口矩阵。
2. 公网只允许必要入口，例如 `/health`、`/calendar/auth/callback`、网页入口等。
3. 写入类、运维类和调试类 API 加统一认证依赖，例如内部 API key、反向代理 allowlist 或仅绑定内网。
4. `/dingtalk/*` HTTP 测试入口如果继续保留，应明确为本地/受控测试入口，生产公网不暴露。

本次已完成最小代码雏形：写入类、调试类和运维类路由已接入 `X-TDL-Internal-Key` 依赖；Nginx 模板也已改成显式允许入口 + 默认 403。仍需生产配置 `INTERNAL_API_KEY`，并由 Frank 确认后再部署。

### S2 - 高风险：工作台 V0 一旦启用，没有真实身份认证

事实：

- `WORKBENCH_V0_ENABLED=false` 默认关闭。
- 启用后，`/workbench`、`/workbench/home`、`/workbench/meeting-review` 进入路由注册。
- 工作台通过 `owner_id` 查询参数过滤视角，但 `owner_id` 只是筛选条件，不是认证。
- 页面会展示 TDL 标题、负责人、截止时间、状态、优先级等管理信息。

判断：

工作台当前作为本机/受控环境只读试验是合理的；但只要公网启用，就会构成管理数据泄露风险。

建议：

1. 保持默认关闭。
2. 正式启用前增加真实登录态、身份映射、权限判断和审计。
3. 不把 `owner_id` URL 参数当作身份。
4. Nginx 层也应单独保护 `/workbench/`。

### S3 - 中风险：日历授权 start 链路可被外部构造

事实：

- `GET /calendar/auth/start?user_id=...` 会为传入用户生成 OAuth state 并跳转钉钉授权页。
- state 使用 `DINGTALK_APP_SECRET` 做 HMAC 签名，15 分钟过期。
- callback 会校验 state、花名册用户、授权账号和请求用户一致。

判断：

callback 安全校验是有的，不能直接冒授权。但 start 入口本身可被任意访问者构造，可能造成授权链接骚扰、误导或枚举管理者 ID 的边界问题。

建议：

1. start 链接优先只通过钉钉工作通知发送给本人。
2. start 入口增加一次性 nonce、短期白名单或简单速率限制。
3. 失败响应避免暴露过多内部用户判断。

### S4 - 中风险：日历 OAuth token 明文存储在数据库

事实：

- `calendar_authorizations` 表保存 `access_token` 和 `refresh_token`。
- 当前字段类型为 Text，未见应用层加密。

判断：

生产数据库一旦被读取，日历授权 token 会直接暴露。当前 token 后续日历写入主要依赖 union_id 和应用 token，但 refresh token 仍是敏感数据。

建议：

1. 增加应用层加密字段，密钥放 `.env` 或云 KMS。
2. 旧 token 迁移时逐条加密，不在日志输出。
3. 长期可考虑只保留必要授权证明和 union_id，减少持久 token 面积。

### S5 - 中风险：部署入口暴露和服务硬化不足

事实：

- `deploy/nginx-tdl.conf` 将 `/tdl/` 整体代理到 backend，没有路径级 allow / deny。
- `scripts/tdl-prod-check.sh` 默认 `StrictHostKeyChecking=no`。
- systemd 服务以 `tdl` 用户运行，但未配置 `NoNewPrivileges`、`PrivateTmp`、`ProtectSystem` 等硬化项。

判断：

当前单机部署足够简单，但生产安全边界主要靠“服务只监听 127.0.0.1 + Nginx 配置正确 + 管理员不误暴露”。下一步若要扩大试用，应把入口暴露范围和服务权限写死到配置里。

建议：

1. Nginx 增加外部路径 allowlist。
2. 写入/调试 API 默认拒绝公网。
3. SSH 检查脚本不要默认关闭 host key 校验，可改成显式 opt-out。
4. systemd 增加最小硬化参数，并确认不影响 `.env`、日志、runtime_state、仓库目录写入。

本次已处理一部分模板：Nginx 已改为 allowlist，systemd 服务模板已增加基础 hardening 参数；仍未部署生产。

### S6 - 低风险：卡片回调异常日志可能包含私有参数

事实：

- 原代码在缺少 action 或 actor 时记录完整 `incoming.content`。
- 该 content 可能包含卡片私有数据和用户提交字段。

处理：

- 本次已改为只记录 `has_action`、`has_actor` 和顶层 `content_keys`，不再输出完整 payload。

### S7 - 低风险：依赖使用范围版本，缺少锁定文件

事实：

- `requirements.txt` 多数依赖使用 `>=` 范围。
- pip-audit 当前未发现已知漏洞。

判断：

范围版本便于快速开发，但生产可复现性和未来漏洞定位较弱。

建议：

1. 保留开发要求文件。
2. 为生产部署补一个锁定文件或生成部署时的版本快照。
3. 部署脚本输出 pip freeze 到运维记录，但不要写入凭证。

## 六、当前结论

当前系统对两人 pilot 的业务链路已经有较好测试覆盖，但安全边界仍停留在“受控部署 + 默认关闭工作台 + 依赖钉钉 Stream 入口”的阶段。

1. HTTP API 入口认证与公网暴露边界。
2. runtime_state + prod check，让后台进程是否真实工作可见。
